    8. Ausführungsthreads

    Dieses Kapitel führt die gleichzeitige Ausführung mehrerer Codeabschnitte innerhalb eines einzigen Programms ein: Threads (Ausführungsthreads) und die Werkzeuge zu ihrer Synchronisierung. Vor etwa zwanzig Jahren hatten die meisten Rechner nur einen Prozessor, und Parallelität war weitgehend eine vom Betriebssystem aufrechterhaltene Illusion. Heute hat selbst der einfachste Laptop mehrere Kerne: Mehrere Threads laufen tatsächlich gleichzeitig, wodurch die hier behandelten Synchronisierungsprobleme noch häufiger auftreten.

    Kotlin hat auf der JVM keine eigenen Threads: Es verwendet die Threads von Java, die seit der ersten Version (1996) über die Klasse [Thread], das Schlüsselwort [synchronized], und die Methoden [wait] und [notify] der Klasse [Object] in Java integriert sind. Java 5 (2004) ergänzte das Paket [java.util.concurrent] und seine Unterpakete [java.util.concurrent.locks] und [java.util.concurrent.atomic]: Sperren, Semaphoren, nebenläufige Collections, Thread-Pools usw. Java 7 ergänzte das [Fork/Join]-Framework, Java 8 führte parallele Streams ein, und Java 21 führte virtuelle Threads ein; all dies hat die Art, wie Server geschrieben werden, grundlegend verändert. Java 25 führt schließlich gebundene Werte mit Gültigkeitsbereich ([ScopedValue]) ein. Alle diese Klassen des JDK-Frameworks sind in Kotlin direkt nutzbar: Das ist eine seiner großen Stärken. Die Kotlin-Standardbibliothek fügt dem einige Funktionen hinzu, die die Verwendung bequemer machen: die Funktion [thread] und die Erweiterungsfunktion [withLock] aus dem Paket [kotlin.concurrent], die Funktion [synchronized] sowie die Annotationen [@Volatile] und [@Synchronized] … Alle diese Werkzeuge behandeln wir in diesem Kapitel.

    Threads sind jedoch nicht Kotlins letztes Wort zur nebenläufigen Programmierung: Seine native Lösung für Asynchronität sind Coroutinen, die in Kapitel 9 vorgestellt werden. Sie basieren auf Threads, und alles, was wir hier behandeln (kritische Abschnitte, Sichtbarkeit von Schreibzugriffen, Deadlocks usw.), bleibt wesentlich, um sie vollständig zu verstehen.

    Die Beispiele befinden sich im Gradle-Projekt [08-threads]. Jedes Programm ist eine Datei in einem Paket mit seinem Namen ([threads01/Threads01.kt] im Paket [threads01] …) und wird mit [gradlew -q run -Pmain=threads01.Threads01Kt] oder über das grüne Dreieck in IntelliJ IDEA ausgeführt. Programmargumente werden mit der Option [--args] an Gradle übergeben: [gradlew -q run -Pmain=threads08.Threads08Kt --args="5"].

    Ein Wort der Vorsicht vorab: Die Ergebnisse eines Multithreading-Programms unterscheiden sich von einem Lauf zum nächsten. Die Reihenfolge, in der Threads Zugriff auf den Prozessor erhalten, hängt vom Betriebssystem, von der Anzahl der Prozessoren und von der Auslastung des Rechners ab. Die in diesem Kapitel wiedergegebenen Ergebnisse wurden auf einem Linux-Rechner mit zwei Prozessoren gewonnen, der mit anderen sehr aktiven Programmen geteilt wurde. Wenn Sie die Beispiele ausführen, erhalten Sie ähnliche Ergebnisse, die aber selten identisch sein werden. Wir geben jeweils an, was reproduzierbar ist und was nicht.

    8.1. Die Klasse Thread

    Wenn eine Anwendung gestartet wird, läuft sie in einem Ausführungsfluss, einem Thread. Die Klasse, die einen Thread modelliert, ist die Klasse [java.lang.Thread] im JDK-Paket. Beachten Sie, dass Kotlin die Java-Accessoren [getXxx()] / [setXxx(…)] (und [isXxx()] für einen Boolean) als Eigenschaften darstellt: Wir schreiben [thread.name = "Main"] statt [thread.setName("Main")]. Die wichtigsten Konstruktoren, Eigenschaften und Methoden der Klasse sind die folgenden:

    Die Methoden [join] und [sleep] lösen die Exception [InterruptedException] aus, wenn der Thread während des Wartens unterbrochen wird. In Java ist dies eine geprüfte Exception (Checked Exception), die behandelt oder in einer [throws]-Klausel deklariert werden muss. Kotlin kennt keine geprüften Exceptions (Kapitel 3): Der Compiler erzwingt nichts. Das bedeutet nicht, dass man ignorieren darf, was diese Exception bedeutet: Darauf gehen wir im Abschnitt über das Unterbrechen von Threads ein.

    Die Klasse [Thread] besitzt außerdem eine Methode [stop], die einen Thread zwangsweise beendete. Sie ist seit Java 1.2 veraltet und löst seit Java 20 lediglich die Exception [UnsupportedOperationException] aus: Das abrupte Anhalten eines Threads könnte die von ihm bearbeiteten Daten in einem inkonsistenten Zustand hinterlassen. Heute bitten wir einen Thread, sich kooperativ zu beenden, indem wir ihn unterbrechen: Das sehen wir uns etwas später an.

    8.2. Ausführungsthreads erzeugen

    Es sind Anwendungen möglich, in denen Codeabschnitte „gleichzeitig“ in verschiedenen Ausführungsthreads laufen. Hat der Rechner weniger Prozessoren als ausführbereite Threads, teilen sich die Threads die Prozessoren: Jeder erhält sie der Reihe nach für einen kurzen Moment (einige Millisekunden). Auf einem Mehrprozessorrechner laufen mehrere Threads tatsächlich gleichzeitig. Die einem Thread zugeteilte Zeit hängt von verschiedenen Faktoren ab, darunter seine Priorität, die einen Standardwert hat, aber programmatisch festgelegt werden kann (Eigenschaft [priority]); dies ist lediglich ein Richtwert, den das Betriebssystem ignorieren darf (Linux ignoriert ihn standardmäßig). Ein Thread, der Zugriff auf den Prozessor hat, kann ihn vorzeitig freigeben:

    • indem er auf ein Ereignis wartet (Beendigung eines anderen Threads mit [join], Warten auf ein Signal);
    • indem er für eine festgelegte Dauer in einen Ruhezustand wechselt ([sleep]).

    Ein Thread T wird zunächst erzeugt, zum Beispiel durch den Konstruktor [Thread(task, name)], wobei [task] ein Objekt ist, das das Java-Interface [Runnable] implementiert, dessen einzige Methode [void run()] ist. Mithilfe der in Kapitel 7 beschriebenen SAM-Konvertierung wird ein Lambda oder eine Funktionsreferenz vom Typ [() -> Unit] anstelle eines [Runnable] übergeben. In älterem Code begegnen uns auch von [Thread] abgeleitete Klassen, die dessen Methode [run] überschreiben: Das wird nicht empfohlen, da es die auszuführende Aufgabe mit den Mitteln ihrer Ausführung vermischt.

    Das Erzeugen eines Threads startet ihn nicht:

    • die Ausführung des Threads T wird durch [T.start()] gestartet: Die Methode [run] der Aufgabe, die dem Konstruktor von T übergeben wurde, wird dann vom Thread T ausgeführt. Der Code, der die Anweisung [T.start()] ausführt, wartet nicht auf das Ende von Thread T: Er geht sofort zur nächsten Anweisung über. Nun laufen zwei Threads parallel. Sie müssen oft miteinander kommunizieren, um den Fortschritt der gemeinsamen Arbeit zu verfolgen: Das ist das Problem der Thread-Synchronisierung;
    • Einmal gestartet, läuft Thread T eigenständig. Er endet, wenn die von ihm ausgeführte Funktion beendet ist;
    • wir können mit [T.join()] auf das Ende seiner Ausführung warten. Das ist eine blockierende Anweisung: Der Thread, der sie ausführt, ist blockiert, bis Thread T seine Arbeit beendet hat. Das ist eine grundlegende Synchronisierungsmethode.

    // Erstellung von Ausführungsthreads
package threads02

import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main() {
    // der Hauptthread erhält einen Namen
    Thread.currentThread().name = "Main"

    // Erstellung von 5 Threads
    val tasks = Array(5) { i ->
        // Thread Nr. i führt die Funktion display aus; er erhält den Namen "i"
        Thread(::display, i.toString())
    }
    // ihre Ausführung wird gestartet (nicht blockierende Operation)
    for (task in tasks) {
        task.start()
    }

    // Ende des Hauptthreads
    println("End of thread ${Thread.currentThread().name} at ${time()}")
}

// die von den Threads ausgeführte Funktion: sie hat die Form von Runnable.run()
fun display() {
    // der Thread, der die Funktion ausführt
    val current = Thread.currentThread()
    println("Start of execution of the display function in thread ${current.name}" +
            " (id ${current.threadId()}) : ${time()}")
    // 1 s schlafen
    sleep(1000)
    println("End of execution of the display function in thread ${current.name} : ${time()}")
}

// [ms] Millisekunden schlafen
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        // der Schlaf wurde unterbrochen: das Interrupt-Flag des Threads wird wiederhergestellt
        Thread.currentThread().interrupt()
    }
}

// die aktuelle Uhrzeit, auf die Millisekunde genau
fun time(): String = LocalTime.now().format(DateTimeFormatter.ofPattern("HH:mm:ss.SSS"))

package threads03

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import kotlin.concurrent.thread

fun main() {
    // der Hauptthread erhält einen Namen
    Thread.currentThread().name = "Main"

    // Erstellung und Start von 5 Daemon-Threads mit den Namen 0, 1, 2…
    for (i in 0..<5) {

        thread(isDaemon = true, name = "$i") {
            display()

    8.3. Einen Thread anhalten: die Unterbrechung

    Wie hält man einen Thread an, bevor er seine Arbeit beendet hat, zum Beispiel wenn der Benutzer einen lang laufenden Vorgang abbricht? Die JVM erlaubt es nicht, einen Thread abzuschießen; sie stellt einen kooperativen Mechanismus namens Unterbrechung bereit:

    • Jeder Thread hat ein Interrupt-Flag, einen Boolean, der anfangs auf [false] gesetzt ist;
    • Ein Thread namens T1, der den Thread T2 beenden möchte, ruft [T2.interrupt()] auf. Dadurch wird das Interrupt-Flag von T2 gesetzt. Das ist eine Aufforderung zur Beendigung: T2 wird nicht beendet; es ist Sache dieses Threads zu entscheiden, wann und wie er sich beendet, damit seine Daten in einem konsistenten Zustand bleiben;
    • wenn T2 in einer Wartemethode blockiert ist ([sleep], [join], [wait] und die meisten blockierenden Methoden in [java.util.concurrent]), wird er aufgeweckt: Die Methode löst die Exception [InterruptedException] aus, und das Interrupt-Flag wird auf [false] zurückgesetzt;
    • Wenn T2 Berechnungen durchführt, ohne jemals zu warten, muss er sein eigenes Flag mit [Thread.currentThread().isInterrupted] in regelmäßigen Abständen prüfen.

    In Java deklarieren blockierende Methoden die geprüfte Ausnahme [InterruptedException]: Der Compiler verlangt vom Programmierer, zu entscheiden, was mit einer Stoppanforderung geschehen soll. Kotlin verlangt dies nicht, die Entscheidung muss aber trotzdem getroffen werden, und sie bleibt dieselbe. Es gibt zwei korrekte Reaktionen: die Ausnahme an den Aufrufer weiterreichen oder sie abfangen und die Aufgabe sauber beenden. Wenn keine der beiden Möglichkeiten besteht, wie in der Funktion [sleep] des Programms [Threads02.kt], wird das Flag über [Thread.currentThread().interrupt()] zurückgesetzt, damit der aufrufende Code die Anforderung weiterhin erkennen kann. package threads05

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter

fun main() {
    // 1 - ein Thread, der die meiste Zeit schläft
    val sleeper = Thread.ofPlatform().name("sleeper").start {
        var round = 0
        try {
            while (true) {
                round++
                println("${time()} : sleeper, round $round")
                // sleep wirft eine InterruptedException, wenn der Thread während des Schlafs unterbrochen wird
                Thread.sleep(400)
            }
        } catch (_: InterruptedException) {
            // die Unterbrechung ist eine Stoppanforderung: der Thread beendet seine Arbeit sauber
            println("${time()} : sleeper interrupted while sleeping, it stops")
        }
    }
    // 2 - ein Thread, der rechnet, ohne jemals zu schlafen
    val calculator = Thread.ofPlatform().name("calculator").start {
        var n = 0L
        // der Thread prüft regelmäßig sein Interrupt-Flag
        while (!Thread.currentThread().isInterrupted) {
            n++
        }
        println("${time()} : calculator interrupted after %,d iterations, it stops".format(n))
    }
    // 3 - ein Thread, der Unterbrechungen ignoriert (nicht nachahmen)
    val deaf = Thread.ofPlatform().name("deaf").daemon().start {
        repeat(10) {
            try {
                Thread.sleep(400)
            } catch (_: InterruptedException) {
                // die Exception wird "verschluckt": die Stoppanforderung geht verloren
                println("${time()} : deaf ignores the interruption and continues")
            }
        }
    }

    // die Threads arbeiten 1 s lang weiter
    Thread.sleep(1000)
    println("${time()} : Main requests the three threads to stop")
    sleeper.interrupt()
    calculator.interrupt()
    deaf.interrupt()
    // auf das Ende jedes Threads warten, höchstens 1 s
    for (thread in listOf(sleeper, calculator, deaf)) {
        val finished = thread.join(Duration.ofSeconds(1))
        println("${time()} : thread ${thread.name} finished: $finished")
    }
}

    8.4. Virtuelle Threads

    Die bisher erstellten Threads sind Plattform-Threads: Jeder von ihnen ist eine Hülle um einen Betriebssystem-Thread, den er während seiner gesamten Lebensdauer belegt. Ein Betriebssystem-Thread ist eine teure Ressource: Seine Erstellung braucht Zeit, sein Stack reserviert Speicher (in der Größenordnung eines Megabytes), und das System kann nicht effizient mehr als einige Tausend davon verwalten. Ein Server, der jedem Client einen Thread zuweist (siehe das Diagramm im folgenden Abschnitt), verbringt jedoch die meiste Zeit mit Warten: auf die Antwort einer Datenbank, auf die nächste Anfrage des Clients … Während dieser Wartezeiten ist der System-Thread blockiert und nicht nutzbar.

    Java 21 führte virtuelle Threads (JEP 444) ein, die in Kotlin unverändert verwendet werden können. Ein virtueller Thread ist ein [Thread]-Objekt wie jedes andere, wird aber von der Java Virtual Machine und nicht vom Betriebssystem verwaltet:

    • Zur Ausführung wird ein virtueller Thread auf einem Plattform-Thread eingebunden (mounted), dem sogenannten „Carrier-Thread“. Die Carrier-Threads bilden einen kleinen Pool, dessen Größe standardmäßig der Anzahl der Prozessoren entspricht;
    • wenn ein virtueller Thread blockiert ([sleep], Warten auf Netzwerk-E/A, eine Sperre, eine blockierende Warteschlange usw.), wird er ausgebunden (unmounted): Sein Stack wird im Speicher der virtuellen Maschine abgelegt, und der Carrier-Thread steht sofort für einen anderen virtuellen Thread zur Verfügung. Wenn die Wartezeit endet, wird der virtuelle Thread wieder an einen Carrier-Thread gebunden – nicht unbedingt an denselben;
    • Ein virtueller Thread belegt einige Hundert Byte: Es lassen sich Millionen davon erstellen.

    Kotlin-Coroutinen (Kapitel 9) beruhen auf einer ähnlichen Idee – einen wartenden Vorgang anzuhalten, ohne einen System-Thread zu blockieren –, werden aber vom Kotlin-Compiler und nicht von der virtuellen Maschine umgesetzt. Beide Ansätze vergleichen wir in Kapitel 9.

    8.5. Der Nutzen von Threads

    Nachdem wir auf die Existenz eines Standard-Threads hingewiesen haben – desjenigen, der die Funktion [main] ausführt – und wissen, wie man weitere erstellt, wollen wir uns den Nutzen von Threads genauer ansehen. Sie haben zwei Hauptverwendungszwecke:

    • alle Prozessoren der Maschine für eine zeitaufwendige Berechnung zu nutzen: Die Arbeit wird in Teile zerlegt, die verschiedenen Threads zugewiesen werden. Das tun wir mit parallelen Streams und dem [Fork/Join]-Framework am Ende dieses Kapitels;
    • mehrere Aufgaben gleichzeitig auszuführen, insbesondere wenn einige davon hauptsächlich aus Warten bestehen (auf eine Netzwerkantwort, einen Lesezugriff auf die Festplatte oder eine Benutzereingabe). Das ist bei Client-Server-Internetanwendungen der Fall, die wir in Kapitel 12 behandeln.

    // vom gestarteten Thread gesetzt

    8.7.2. Die Funktion synchronized und die Annotation @Synchronized

    In Java begrenzt der Block [synchronized] einen kritischen Abschnitt wie folgt: [synchronized (lock) { …critical section… }]. [lock] ist ein Objekt, das für alle Threads sichtbar ist, die den kritischen Abschnitt ausführen. Auf der JVM besitzt jedes Objekt eine interne Sperre, auch Monitor genannt. Der Block [synchronized] stellt sicher, dass nur ein Thread zur Zeit den Monitor des Objekts [lock] hält, das heißt, dass nur ein Thread zur Zeit den kritischen Abschnitt ausführt: Ein Thread, der auf einen von einem anderen Thread gehaltenen Monitor trifft, wird blockiert, bis der Monitor freigegeben wird. Der Monitor wird beim Verlassen des Blocks freigegeben, unabhängig davon, ob der Block normal oder aufgrund einer Ausnahme verlassen wird.

    Kotlin hat kein Schlüsselwort [synchronized]. Stattdessen stellt die Standardbibliothek eine [synchronized] -Funktion bereit, deren Signatur [inline fun <R> synchronized(lock: Any, block: () -> R): R] lautet. // die gemeinsame Ressource
object Counter {
    // der Thread-Zähler
    private var counter = 0
    // das Synchronisationsobjekt, für alle Threads sichtbar
    private val lock = Any()

    // der Wert des Zählers, gelesen unter dem Schutz des Locks
    val value: Int
        get() = synchronized(lock) { counter }

    // die von jedem Thread ausgeführte Funktion
    fun increment() {
        val name = Thread.currentThread().name
        println("At ${time()}, thread $name is waiting for permission to enter the critical section")
        // nur ein Thread gleichzeitig führt den folgenden Block aus

            println("At ${time()}, thread $name read the counter value: $v")

            sleep(1000)

            counter = v + 1
            println("At ${time()}, thread $name wrote the counter value: $counter")
        }
        println("At ${time()}, thread $name left the critical section")
    }
}

    8.7.4. Prozesse synchronisieren: die Dateisperre

    Die bisherigen Sperren synchronisieren Threads innerhalb derselben virtuellen Maschine, also innerhalb desselben Prozesses. Manchmal müssen verschiedene Prozesse eine Ressource wie eine Datei gemeinsam nutzen, oder man möchte verhindern, dass zwei Instanzen derselben Anwendung gestartet werden. Die JVM stellt kein benanntes, zwischen Prozessen geteiltes Synchronisierungsobjekt bereit; dafür verwendet man eine vom Betriebssystem verwaltete Dateisperre : die Klasse [java.nio.channels.FileLock]. Eine Sperre wird auf einer geöffneten Datei in Form eines [FileChannel]-Kanals erworben:

    • [lock(): FileLock]: wartet, bis die Sperre verfügbar ist, und erwirbt sie;
    • [tryLock(): FileLock?]: versucht, die Sperre ohne Warten zu erwerben, und liefert [null] , wenn sie von einem anderen Prozess gehalten wird. Kotlin behandelt den Rückgabewert dieser Java-Methode als plattformspezifischen Typ ([FileLock!]); der Programmierer muss ihn so behandeln, als könnte er [null] sein;
    • [release()]: gibt die Sperre frei. Die Sperre wird auch freigegeben, wenn der Kanal geschlossen wird oder der Prozess endet, selbst bei abruptem Abbruch: Eine Sperre kann nicht „verwaist“ bleiben. Die Klasse [FileLock] implementiert die Schnittstelle [AutoCloseable]: Ihre Methode [close] ruft [release] auf, und die Kotlin-Funktion [use] kann die Sperre daher freigeben.

    8.7.5. Eine Barriere: die Klasse Semaphore

    Ein Semaphor ist ein Zähler für Permits (oder Plätze). Die Klasse [java.util.concurrent.Semaphore] stellt die folgenden Methoden bereit:

    Element
    Rolle
    [Semaphore(permits: Int)], [Semaphore(permits: Int, fair: Boolean)]
    erstellt einen Semaphor mit [permits] Permits; der zweite Parameter hat dieselbe Bedeutung wie bei [ReentrantLock]
    [acquire()]
    erwirbt ein Permit. Sind keine Permits mehr vorhanden, wird der Thread blockiert, bis ein Permit zurückgegeben wird. Das Warten kann unterbrochen werden ([InterruptedException])
    [acquireUninterruptibly()]
    wie oben, aber das Warten kann nicht unterbrochen werden

    Erhält ein Permit ohne Warten oder mit einer Wartezeit von höchstens [timeout]; liefert [false] im Fehlerfall

    gibt ein Permit zurück (fügt es hinzu); einer der wartenden Threads kann es dann nehmen

    Anders als eine Sperre gehört ein Permit keinem bestimmten Thread: Jeder Thread kann [release] aufrufen, auch wenn er nie ein Permit erworben hat. Ein mit null Permits erstellter Semaphor ist daher eine geschlossene Barriere, an der Threads, die [acquire] aufrufen, blockiert werden. Ein anderer Thread öffnet sie zum gegebenen Zeitpunkt durch Aufruf von [release]. Dieser Zeitpunkt hängt vollständig vom zu lösenden Problem ab. Der Thread, der das einzige Permit erworben hat, ist durch die Barriere gegangen, die sich hinter ihm geschlossen hat; indem er das Permit zurückgibt, öffnet er die Barriere für einen anderen Thread. package threads13

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.Semaphore
import kotlin.system.exitProcess

// die gemeinsame Ressource
object Counter {
    // der Thread-Zähler
    var value = 0
        private set
    // die Barriere: ein ohne Berechtigung erstelltes und damit geschlossenes Semaphor
    val sync = Semaphore(0)

    // die von jedem Thread ausgeführte Funktion
    fun increment() {
        val name = Thread.currentThread().name
        println("At ${time()}, thread $name is waiting for permission to enter the critical section")
        // Überqueren der Barriere: der Thread nimmt die einzige Berechtigung, die Barriere schließt sich hinter ihm
        sync.acquireUninterruptibly()
        try {
            // Lesen des Zählers
            val v = value
            println("At ${time()}, thread $name read the counter value: $v")
            // Warten
            sleep(1000)
            // Inkrementieren des Zählers
            value = v + 1
            println("At ${time()}, thread $name wrote the counter value: $value")
        } finally {
            // die Berechtigung wird zurückgegeben: die Barriere öffnet sich für einen anderen Thread
            println("At ${time()}, thread $name leaves the critical section")
            sync.release()
        }
    }
}

fun main(args: Array<String>) {
    // Überprüfung des Arguments: die Anzahl der zu erstellenden Threads
    val nbMaxThreads = 100
    val nbThreads = args.singleOrNull()?.toIntOrNull() ?: -1
    if (nbThreads !in 1..nbMaxThreads) {
        System.err.println("syntax: threads13.Threads13Kt nbThreads (nbThreads between 1 and $nbMaxThreads)")
        exitProcess(1)
    }

    // Erstellung und Start der Threads
    val threads = List(nbThreads) { i -> Thread(Counter::increment, "$i") }
    threads.forEach { it.start() }
    // die Threads dürfen die geschlossene Barriere erreichen
    Thread.sleep(500)
    // die Barriere des kritischen Abschnitts wird geöffnet
    Thread.currentThread().name = "Main"
    println("At ${time()}, thread Main opens the barrier of the critical section")
    Counter.sync.release()
    // Warten auf das Ende der Threads
    threads.forEach { it.join() }
    // Anzeige des Zählers
    println("Number of threads generated: ${Counter.value}")
}

// [ms] Millisekunden schlafen
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
}

    8.7.7. Sichtbarkeit von Schreibzugriffen: die Annotation @Volatile

    Sperren dienen nicht nur dazu, eine Gruppe von Operationen unteilbar zu machen. Sie lösen ein zweites, heimtückischeres Problem: die Sichtbarkeit von Schreibzugriffen. Um schneller zu sein, legt der Prozessor Werte in seinen Registern und Caches ab, und der Compiler ordnet Lese- und Schreibzugriffe im laufenden Betrieb um oder eliminiert sie, wie wir beim Programm [Threads09.kt] gesehen haben. Das Ergebnis: Ein von einem Thread geschriebener Wert ist für einen anderen Thread möglicherweise erst später sichtbar – oder vielleicht nie.

    Das Java-Speichermodell , das alle von der JVM ausgeführten Programme – einschließlich Kotlin-Programmen – bestimmt, definiert genau, wann ein Schreibzugriff garantiert sichtbar ist: wenn zwischen dem Schreib- und dem Lesezugriff eine „Happens-before“-Beziehung besteht. Die wichtigsten sind die folgenden:

    • Alles, was ein Thread vor der Freigabe einer Sperre getan hat (Ende eines [synchronized]-Blocks, [unlock]), ist für den Thread sichtbar, der anschließend diese Sperre erwirbt;
    • was der aufrufende Thread vor [start] getan hat, ist für den aufgerufenen Thread sichtbar; was ein Thread getan hat, ist für den Thread sichtbar, der über [join] auf sein Ende gewartet hat;
    • ein Schreibzugriff auf ein [volatile] -Feld ist für jeden nachfolgenden Lesezugriff auf dieses Feld sichtbar;
    • die Werkzeuge in [java.util.concurrent] bieten ähnliche Garantien: Was ein Thread vor [release()], [countDown()], oder dem Einfügen eines Elements in eine nebenläufige Collection getan hat, ist für den Thread sichtbar, der anschließend [acquire()], [await()], ausführt oder das Element abruft.

    Besteht keine dieser Beziehungen, spricht man davon, dass das Programm einen „Data Race“ enthält, und es gibt keine Garantien. In Java wird ein Feld mit einem Schlüsselwort als [volatile] deklariert; Kotlin hat dieses Schlüsselwort nicht, aber eine Annotation, [@Volatile], die auf eine Eigenschaft [var] angewendet wird: Das Feld, das die Eigenschaft speichert, ist dann ein Java-Feld [volatile]. Das Programm [Threads16.kt] zeigt seinen Nutzen in einem häufigen Szenario: einem Flag, das einen Thread zum Stoppen auffordert.

    var volatileStop = false
}

    8.7.8. Atomare Klassen

    Das Paket [java.util.concurrent.atomic] (Java 5) stellt Klassen bereit, die einfache Operationen auf einer Variablen atomar machen: Die Operation wird vom Thread vollständig ausgeführt, ohne dass ein anderer Thread die Variable mitten in der Operation beobachten oder ändern könnte. Die bisherigen Werkzeuge ([synchronized], [ReentrantLock], [Semaphore]) sind alle dazu gedacht, eine Gruppe von Operationen atomar zu machen, auf Kosten der Blockierung anderer Threads. object Counter {
    // @Volatile garantiert die Sichtbarkeit von Schreibzugriffen, nicht die Atomarität von value++
    @Volatile
    var value = 0
    private val lock = Any()
    private val reentrantLock = ReentrantLock()
    val atomic = AtomicInteger()
    val adder = LongAdder()

    // Zurücksetzen der Zähler
    fun reset() {
        value = 0
        atomic.set(0)
        adder.reset()
    }

    // lesen, inkrementieren, schreiben: nicht atomar
    fun withoutSynchronization() {
        value++
    }

    // kritischer Abschnitt, geschützt durch synchronized
    fun withSynchronized() {
        synchronized(lock) {
            value++
        }
    }

    // synchronized-Funktion: das Lock ist das Counter-Objekt selbst
    @Synchronized
    fun withSynchronizedAnnotation() {
        value++
    }

    // kritischer Abschnitt, geschützt durch ein ReentrantLock
    fun withReentrantLock() {
        reentrantLock.withLock {
            value++
        }
    }

    // atomares Inkrementieren, ohne Lock
    fun withAtomicInteger() {
        atomic.incrementAndGet()
    }

    // Inkrementieren eines verteilten Addierers, ohne Lock
    fun withLongAdder() {
        adder.increment()
    }

fun measure(method: String, nbThreads: Int, nbIncrements: Int, increment: () -> Unit, value: () -> Long) {
    Counter.reset()
    // ein Startsignal, damit alle Threads gleichzeitig beginnen
    val startSignal = CountDownLatch(1)
    val threads = List(nbThreads) {
        Thread.ofPlatform().start {
            try {
                startSignal.await()
            } catch (_: InterruptedException) {
                return@start
            }
            repeat(nbIncrements) { increment() }
        }
    }
    // los!
    val begin = System.nanoTime()
    startSignal.countDown()
    threads.forEach { it.join() }
    val duration = (System.nanoTime() - begin) / 1_000_000
    println("%-23s : value obtained %,12d in %5d ms".format(method, value(), duration))
}

    8.8. Gleichzeitiger Zugriff auf mehrere gemeinsame Ressourcen

    8.8.1. Deadlock

    In unseren bisherigen Beispielen wurde eine einzige Ressource von den verschiedenen Threads gemeinsam genutzt. Die Situation wird komplizierter, wenn es mehrere Ressourcen gibt, die voneinander abhängen. Insbesondere kann ein Deadlock auftreten: Zwei Threads warten aufeinander. Betrachten wir die folgenden Aktionen, die nacheinander ablaufen:

    • Ein Thread T1 erwirbt die Sperre V1, um auf eine gemeinsame Ressource R1 zuzugreifen;
    • ein Thread T2 erwirbt die Sperre V2, um auf eine gemeinsame Ressource R2 zuzugreifen;
    • Der Thread T1 fordert die Sperre V2 an. Er wird blockiert;
    • der Thread T2 fordert die Sperre V1 an. Er wird blockiert.

    Die Threads T1 und T2 warten unbegrenzt aufeinander. Es sind mehrere Lösungen möglich:

    • beide Ressourcen gleichzeitig mit einer einzigen Sperre anfordern. Das ist nicht immer möglich, wenn dadurch eine kostspielige Ressource lange gesperrt wird;
    • Sperren immer in derselben Reihenfolge erwerben: Wenn alle Threads V1 vor V2 erwerben, ist ein Deadlock ausgeschlossen. Das ist die am häufigsten verwendete Regel;
    • Ein Thread, der V1 hält und V2 nicht erwerben kann, gibt V1 frei, um einen Deadlock zu vermeiden.

// nimmt die 1. Ressource und versucht dann, während [timeout] die 2. zu nehmen
fun work(first: Lock, firstName: String, second: Lock, secondName: String, timeout: Duration) {
    val name = Thread.currentThread().name
    first.withLock {
        println("${time()} : $name obtained $firstName")
        try {
            // dem anderen Thread wird Zeit gegeben, seine erste Ressource zu nehmen
            Thread.sleep(500)
            println("${time()} : $name requests $secondName")
            // Anforderung mit maximaler Wartezeit, statt eines lock(), das unbegrenzt warten würde
            if (second.tryLock(timeout.inWholeMilliseconds, TimeUnit.MILLISECONDS)) {
                try {
                    println("${time()} : $name obtained $secondName" +
                            " and works with $firstName and $secondName")
                } finally {
                    second.unlock()
                }
            } else {
                println("${time()} : $name did not obtain $secondName in ${timeout.inWholeSeconds} s:" +
                        " it releases $firstName and gives up")
            }
        } catch (_: InterruptedException) {
            Thread.currentThread().interrupt()
        }
    }
}

    8.8.2. Ein Beispiel: Leser und Schreiber

    Betrachten wir das folgende Beispiel:

    • Wir haben ein Array, in das einige Threads Daten schreiben (die Schreiber) und andere sie lesen (die Leser);
    • die Schreiber sind untereinander gleichberechtigt, schließen sich aber gegenseitig aus: Nur ein Schreiber zur Zeit kann Daten im Array ablegen;
    • die Leser sind untereinander gleichberechtigt, schließen sich aber gegenseitig aus: Nur ein Leser zur Zeit kann die im Array gespeicherten Daten lesen;
    • ein Leser kann nur dann Daten aus dem Array lesen, wenn ein Schreiber welche dort abgelegt hat, und ein Schreiber kann nur dann neue Daten im Array ablegen, wenn die bereits dort vorhandenen Daten von einem Leser gelesen wurden.

    Es gibt zwei Arten gemeinsamer Ressourcen:

    • das beschreibbare Array: Nur ein Schreiber zur Zeit darf darauf zugreifen;
    • das lesbare Array: Nur ein Leser zur Zeit darf darauf zugreifen.

    und eine Reihenfolge für die Nutzung dieser Ressourcen:

    • Ein Leser muss immer auf einen Schreiber folgen;
    • ein Schreiber muss immer auf einen Leser folgen, außer beim ersten Mal.

    Der Zugriff auf diese beiden Ressourcen lässt sich mit zwei Barrieren vom Typ [Semaphore] steuern:

    • Die Barriere [canWrite] steuert den Zugriff der Schreiber auf das Array;
    • die Barriere [canRead] steuert den Zugriff der Leser auf das Array;
    • Die Barriere [canWrite] wird im geöffneten Zustand erstellt (ein Permit), lässt den ersten Schreiber passieren und blockiert alle anderen;
    • Die Barriere [canRead] wird im geschlossenen Zustand erstellt (kein Permit) und blockiert alle Leser;
    • Hat ein Schreiber seine Arbeit beendet, öffnet er die Barriere [canRead] , um einen Leser hereinzulassen;
    • Wenn ein Leser seine Arbeit beendet hat, öffnet er die Schranke [canWrite] , um einen Schreiber hereinzulassen.

    8.8.3. Die Methoden wait und notifyAll

    Wenn im vorherigen Beispiel Schreiber an der Anweisung [canWrite.acquireUninterruptibly()] blockiert sind, wird einer von ihnen – irgendeiner – durch die Operation [canWrite.release()] freigegeben. Wenn Sie die Schranke für einen bestimmten Schreiber öffnen möchten, wird es komplizierter.

    Stellen Sie sich als Analogie ein Amt mit Bedienschaltern vor. Wenn ein Kunde eintrifft, zieht er am Spender eine nummerierte Wartemarke und setzt sich dann hin. Die Kunden werden per Lautsprecher mit ihrer Nummer aufgerufen. Während des Wartens kann der Kunde tun, was er will: lesen oder dösen. Er wird jedes Mal geweckt, wenn der Lautsprecher eine Nummer ausruft. Ist es seine Nummer, steht der Kunde auf und geht zum Schalter; andernfalls widmet er sich wieder dem, was er zuvor getan hat. Ähnlich können wir bei Threads vorgehen. Nehmen wir das Beispiel der Schreiber:

Dennoch ist es nützlich, [wait] und [notifyAll] zu kennen, die man in viel bestehendem Java-Code antrifft.

    Wir beschreiben nun ein Standardmuster – das unter anderem im Buch von Brian Goetz et al., [Java Concurrency in Practice], vorgestellt wird –, mit dem sich Schrankenprobleme mit Zutrittsbedingungen lösen lassen.

    Threads, die sich eine Ressource (den Zähler) teilen, greifen über ein Objekt darauf zu, das wir Token nennen: Es ist ein einfaches Objekt ([Object()]), dessen Monitor verwendet wird. Um die Schranke zum Zähler zu passieren, muss man das Token besitzen, und es gibt nur eines. Die Threads müssen das Token daher untereinander weiterreichen.

    Um zum Schalter zu gelangen, fordert ein Thread zunächst das Token mit einem Block [synchronized(token) { … }] an. Erhält er das Token, prüft er in einer Schleife [while (!iAmTheExpectedOne) { token.wait() }], ob er die Bedingung erfüllt, um zum Schalter zu gehen, und geht dann – weiterhin innerhalb des Blocks [synchronized] – zum Schalter. Ist der Thread nicht der am Schalter erwartete, gibt er seinen Platz ab, indem er das Token über [token.wait()] zurückgibt und in den blockierten Zustand wechselt. Er wird geweckt, wenn ein anderer Thread eine Änderung der Zutrittsbedingung signalisiert; er erhält dann das Token zurück und prüft die Bedingung erneut. Deshalb ist der Test eine Schleife ([while]) und kein einfaches [if]. Es gibt einen zweiten, JVM-spezifischen Grund: Die Spezifikation erlaubt „Spurious Wakeups“ (unbegründetes Aufwachen), bei denen [wait] endet, ohne dass ein Thread [notify] aufgerufen hat; die Schleife macht sie unschädlich. Die Operation [token.wait()] kann nur von einem Thread ausgeführt werden, der den Monitor des Tokens hält; andernfalls wird eine Exception [IllegalMonitorStateException] ausgelöst. In diesem Schema wird das Token erst nach Abschluss der Transaktion freigegeben.

    Der Thread, der die Zutrittsbedingung zum Zähler ändert, muss ebenfalls das Token halten und die wartenden Threads benachrichtigen: Innerhalb eines Blocks [synchronized(token) { … }] ändert er die Zutrittsbedingung zum Zähler und weckt dann die wartenden Threads mit [token.notifyAll()] auf.

    Das Aufwecken der Threads bedeutet, dass die wartenden Threads zu Kandidaten für das Token werden; sie erhalten es nicht sofort. Das Token ist erst am Ende des Blocks [synchronized] verfügbar. Alle aufgeweckten Threads erhalten das Token dann der Reihe nach in unbestimmter Reihenfolge, wodurch sie die Gelegenheit haben, die Zutrittsbedingung erneut zu prüfen. Der erste, der die Bedingung erfüllt, behält das Token und geht zum Schalter.

package threads20

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import kotlin.concurrent.thread
import kotlin.random.Random

fun main() {
    // die Anzahl der Threads jeder Art
    val nbThreads = 3

    // die Reihenfolge der Leser: umgekehrt zur Erstellungsreihenfolge
    Board.readOrder = List(nbThreads) { i -> "R${nbThreads - 1 - i}" }
    // die Reihenfolge der Schreiber: die Erstellungsreihenfolge
    Board.writeOrder = List(nbThreads) { i -> "W$i" }
    for (i in 0..<nbThreads) {
        println("Reader ${Board.readOrder[i]} is in position $i," +
                " writer ${Board.writeOrder[i]} is in position $i")
    }

    // Erstellung und Start der Leser-Threads, dann der Schreiber-Threads
    repeat(nbThreads) { i -> thread(name = "R$i") { Board.read() } }
    repeat(nbThreads) { i -> thread(name = "W$i") { Board.write() } }

    // Schreibberechtigung
    Board.allowWriting()
    // Ende von main
    println("End of Main...")
}

// die gemeinsame Ressource und ihre Synchronisation
object Board {
    // das zwischen Lesern und Schreibern gemeinsam genutzte Array
    private val data = IntArray(3)
    // die Zugriffstoken der Lese- und Schreibzähler:
    // java.lang.Object-Objekte, um wait und notifyAll zu haben
    @Suppress("PLATFORM_CLASS_MAPPED_TO_KOTLIN")
    private val canRead = Object()
    @Suppress("PLATFORM_CLASS_MAPPED_TO_KOTLIN")
    private val canWrite = Object()
    // die Zugriffsbedingungen der Zähler
    private var readingAllowed = false
    private var writingAllowed = false
    private var nextReader = 0
    private var nextWriter = 0
    // die Reihenfolge der Leser und der Schreiber
    var readOrder = listOf<String>()
    var writeOrder = listOf<String>()

    // öffnet den Schreibzähler
    fun allowWriting() {
        synchronized(canWrite) {
            writingAllowed = true
            // wir wecken alle Schreiber auf, die auf das Token warten
            canWrite.notifyAll()
        }
    }

    // den Inhalt des Arrays lesen
    fun read() {
        val name = Thread.currentThread().name
        println("Function [read] started by thread $name")
        // das Token des Lesezählers wird angefordert
        synchronized(canRead) {
            try {
                // solange wir nicht an der Reihe sind, geben wir das Token zurück und warten
                while (!readingAllowed || readOrder[nextReader] != name) {
                    canRead.wait()
                }
            } catch (_: InterruptedException) {
                return
            }
            // am Zähler: Lesen des Arrays
            for (number in data) {
                sleep(500)
                println("${time()} : reader $name read the number $number")
            }
            // nächster Leser
            readingAllowed = false
            nextReader++
            // die Schreiber erfahren, dass sie schreiben können
            synchronized(canWrite) {
                writingAllowed = true
                canWrite.notifyAll()
            }
            println("Function [read] finished by thread $name")
        }
    }

    // in das Array schreiben
    fun write() {
        val name = Thread.currentThread().name
        println("Function [write] started by thread $name")
        // das Token des Schreibzählers wird angefordert
        synchronized(canWrite) {
            try {
                // solange wir nicht an der Reihe sind, geben wir das Token zurück und warten
                while (!writingAllowed || writeOrder[nextWriter] != name) {
                    canWrite.wait()
                }
            } catch (_: InterruptedException) {
                return
            }
            // am Zähler: Schreiben des Arrays
            for (i in data.indices) {
                sleep(500)
                data[i] = Random.nextInt(0, 1000)
                println("${time()} : writer $name wrote the number ${data[i]}")
            }
            // nächster Schreiber
            writingAllowed = false
            nextWriter++
            // die Leser erfahren, dass sie lesen können
            synchronized(canRead) {
                readingAllowed = true
                canRead.notifyAll()
            }
            println("Function [write] finished by thread $name")
        }
    }
}

    8.8.4. Bedingungen: Die Schnittstelle Condition

    Die Methoden [wait] und [notifyAll] sind dem Monitor eines Objekts und damit den Blöcken [synchronized] zugeordnet. Für einen Lock [ReentrantLock] ist das Äquivalent die Schnittstelle [java.util.concurrent.locks.Condition]: Ein Objekt [Condition] wird von der Methode [newCondition()] des Locks erzeugt und stellt die Methoden [await()] (das Äquivalent von [wait]), [await(time: Long, unit: TimeUnit)], [signal()] (das Äquivalent von [notify]) und [signalAll()] (das Äquivalent von [notifyAll]) bereit. Für ihre Verwendung gelten dieselben Regeln: Der Thread muss den Lock halten, und die Zutrittsbedingung wird innerhalb einer Schleife [while] getestet. Es handelt sich um Standardmethoden einer Java-Schnittstelle: Kotlin ruft sie ohne Typumwandlung und ohne Warnungen auf. Dies ist die in Kotlin bevorzugte Lösung.

    private val canWrite = lock.newCondition()

    private var writingAllowed = false
    private var nextReader = 0
    private var nextWriter = 0
    // die Reihenfolge der Leser und der Schreiber
    var readOrder = listOf<String>()
    var writeOrder = listOf<String>()

    fun allowWriting() {
        lock.withLock {
            writingAllowed = true
            // wir wecken alle Schreiber auf, und nur diese
            canWrite.signalAll()
        }
    }

        println("Function [read] started by thread $name")

            try {
                // solange wir nicht an der Reihe sind, geben wir das Lock zurück und warten auf ein Signal

                    canRead.await()

                return

    8.8.5. Mehrere gleichzeitige Leser: ReadWriteLock

    In den vorherigen Beispielen waren die Leser exklusiv. In vielen Anwendungen ist das unnötig restriktiv: Mehrere Threads können gleichzeitig Daten lesen, die niemand verändert. Nur Schreibzugriffe müssen exklusiv sein: Während ein Schreiber die Daten ändert, darf weder ein Leser noch ein anderer Schreiber darauf zugreifen. Dies ist das klassische Leser-Schreiber-Problem, das von der Schnittstelle [java.util.concurrent.locks.ReadWriteLock] gelöst wird. Ein Objekt [ReadWriteLock] stellt zwei verknüpfte Locks bereit:

    • [readLock()]: der Lese-Lock, der von mehreren Threads gleichzeitig gehalten werden kann, solange kein Thread den Schreib-Lock hält;
    • [writeLock()]: der Schreib-Lock, der exklusiv ist.

    Die Kotlin-Standardbibliothek ergänzt zwei Erweiterungsfunktionen aus dem Paket [kotlin.concurrent] für die Klasse [ReentrantReadWriteLock] – die diese Schnittstelle implementiert –, die [withLock] entsprechen: [read { … }] führt den Block aus, während der Lese-Lock gehalten wird, und [write { … }] führt den Block aus, während der Schreib-Lock gehalten wird; beide geben den Lock am Ende des Blocks frei und liefern den Wert des Blocks zurück. class Catalog {
    private val prices = mutableMapOf("keyboard" to 20, "mouse" to 10)
    // ein Lock für die Leser, ein Lock für die Schreiber
    private val lock = ReentrantReadWriteLock()

    // mehrere Threads können gleichzeitig das Lese-Lock halten
    fun readPrice(article: String): Int = lock.read {
        val name = Thread.currentThread().name
        println("${time()} : $name starts reading the price of $article")
        // langes Lesen
        sleep(1000)
        val p = prices.getValue(article)
        println("${time()} : $name read the price of $article: $p")
        p
    }

    // das Schreiblock ist exklusiv: kein Leser, kein anderer Schreiber
    fun changePrice(article: String, newPrice: Int) {
        val name = Thread.currentThread().name
        println("${time()} : $name requests the write lock")
        lock.write {
            println("${time()} : $name starts changing the price of $article")
            // langes Schreiben
            sleep(1000)
            prices[article] = newPrice
            println("${time()} : $name set the price of $article to $newPrice")
        }
    }
}

    8.9. Nebenläufige Collections

    Die vorherigen Beispiele schützten sehr einfache gemeinsame Daten (einen Zähler, ein Array, ein kleines Dictionary). Wenn Threads sich eine Collection (Liste, Dictionary, Warteschlange) teilen, könnte man jeden Zugriff mit einem Lock schützen. Aber gewöhnliche veränderbare Collections – die von Kotlin ([mutableListOf], [mutableMapOf], [ArrayDeque]) ebenso wie die von Java ([ArrayList], [HashMap]) – sind nicht dafür ausgelegt, von mehreren Threads gleichzeitig verändert zu werden: Eine ungeschützte Verwendung kann zum Verlust von Elementen führen, unerwartete Exceptions ([ConcurrentModificationException]) auslösen oder sogar die interne Struktur der Collection beschädigen. Dasselbe gilt für die „schreibgeschützten“ Collections von Kotlin ([List], [Map]): Dieser Typ hindert den Code, der sie erhält, daran, die Collection zu ändern, garantiert aber nicht, dass niemand sonst sie ändert. Die Methoden [Collections.synchronizedList(…)], [Collections.synchronizedMap(…)] … verpacken eine gewöhnliche Collection in ein Objekt, in dem jede Methode vom Typ [synchronized] ist: Das ist sicher, aber alle Threads konkurrieren um einen einzigen Lock, und die Iteration über die Collection muss weiterhin manuell geschützt werden. Seit Java 5 bietet das Paket [java.util.concurrent] Collections, die dafür ausgelegt sind, ohne expliziten Lock von Threads gemeinsam genutzt zu werden. Die Kotlin-Standardbibliothek hat dafür auf der JVM kein Gegenstück: Wir verwenden direkt die des JDK, die die Schnittstellen [MutableList] und [MutableMap] implementieren … und daher genau wie Kotlin-Collections gehandhabt werden ([+=], [[ ]], [for], [filter], [map] …):

    8.9.2. Produzenten und Konsumenten: BlockingQueue

    Das Leser-Schreiber-Problem ist eine Variante des klassischen Produzenten-Konsumenten-Problems: Threads erzeugen Daten, die andere Threads verbrauchen. Die Schnittstelle [BlockingQueue<E>] löst es ohne explizite Synchronisationswerkzeuge:

    • [put(element)] reiht ein Element in die Warteschlange ein. Hat die Warteschlange eine begrenzte Kapazität und ist voll, wird der Produzent blockiert, bis ein Platz frei wird;
    • [take()] entnimmt das Element am Anfang der Warteschlange. Ist die Warteschlange leer, wird der Konsument blockiert, bis ein Element eintrifft;
    • [offer(element, timeout, unit)] und [poll(timeout, unit)] tun dasselbe mit einer maximalen Wartezeit; [offer(element)] und [poll()], die kein Timeout haben, blockieren nie: Sie liefern im Fehlerfall [false] oder [null] (in Kotlin liefert [poll] einen Plattformtyp, [Int!], der wie ein [Int?] behandelt werden sollte).

    Die Warteschlange weiß nicht, dass die Produktion beendet ist. Eine klassische Technik besteht darin, am Ende der Produktion einen speziellen Wert – im Englischen „Poison Pill“ genannt – in die Warteschlange zu legen: Der Konsument, der ihn entnimmt, weiß, dass er aufhören muss. package threads24

import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.ArrayBlockingQueue
import java.util.concurrent.BlockingQueue
import kotlin.concurrent.thread

// der Wert, der das Ende der Produktion signalisiert ("Poison Pill")
const val END = -1

fun main() {
    // eine Warteschlange mit höchstens 3 Elementen
    val queue: BlockingQueue<Int> = ArrayBlockingQueue(3)
    val nbConsumers = 2

    // der Producer legt 8 Zahlen ab und signalisiert dann, dass er fertig ist
    val producer = thread(start = false, name = "P") {
        try {
            for (i in 1..8) {
                // blockierend, wenn die Warteschlange voll ist
                queue.put(i)
                println("${time()} : P put $i (waiting elements: ${queue.size})")
                Thread.sleep(100)
            }
            // eine Endmarkierung pro Consumer
            repeat(nbConsumers) { queue.put(END) }
            println("${time()} : P has finished")
        } catch (_: InterruptedException) {
            Thread.currentThread().interrupt()
        }
    }

    // zwei Consumer nehmen die Zahlen bis zur Endmarkierung
    val consumers = List(nbConsumers) { i ->
        thread(start = false, name = "C${i + 1}") {
            val name = Thread.currentThread().name
            try {
                while (true) {
                    // blockierend, wenn die Warteschlange leer ist
                    val number = queue.take()
                    if (number == END) break
                    println("${time()} : $name took $number")
                    // Verarbeitung der Zahl
                    Thread.sleep(600)
                }
                println("${time()} : $name has finished")
            } catch (_: InterruptedException) {
                Thread.currentThread().interrupt()
            }
        }
    }

    // Start und Warten auf alle Threads
    val all = listOf(producer) + consumers
    all.forEach { it.start() }
    all.forEach { it.join() }
}

    8.10. Thread-Pools: ExecutorService

    8.10.1. Das Prinzip

    Bisher haben wir Threads verwaltet, indem wir sie erstellt und dann gestartet haben, entweder über [start()] oder die Funktion [thread]. Das Erstellen eines Plattform-Threads ist eine relativ teure Operation: Insbesondere muss das System ihm einen Stack zuweisen, und jeder Thread belegt Speicher, solange er existiert. Wir werden in Kapitel 10 sehen, dass es Verbindungspools gibt: Geöffnete Verbindungen werden in Reserve gehalten und an Threads verliehen, die sie anfordern, da das Öffnen einer Verbindung aufwendig ist. Ein ähnliches System gibt es für Threads: den Thread-Pool.

    Die JDK-Klasse repräsentiert einen Thread-Pool über die Schnittstelle [java.util.concurrent.ExecutorService] (einen „Executor“): Es werden keine Threads mehr erstellt; stattdessen werden dem Executor Aufgaben zugewiesen, die er von seinen Threads ausführen lässt. Ein Thread, der eine Aufgabe abgeschlossen hat, wird nicht zerstört; er übernimmt die nächste Aufgabe. Die Klasse [ThreadPoolExecutor], die gängigste Implementierung, funktioniert wie folgt:

    • Sie hat eine feste Anzahl von Threads („Core Pool Size“): Solange diese Anzahl nicht erreicht ist, löst jede neue Aufgabe die Erstellung eines neuen Threads aus;
    • darüber hinaus werden Aufgaben in eine Warteschlange (eine [BlockingQueue]) gestellt, aus der die Threads sie entnehmen;
    • Ist die Warteschlange voll, erstellt der Pool zusätzliche Threads bis zu einer maximalen Anzahl („Maximum Pool Size“). Diese zusätzlichen Threads werden zerstört, wenn sie länger als eine bestimmte Zeit inaktiv bleiben;
    • Ist das Maximum erreicht und die Warteschlange voll, wird die Aufgabe abgelehnt: Standardmäßig löst die Methode, die sie eingereicht hat, die Exception [RejectedExecutionException] aus.

    Der Thread-Pool bietet zwei Vorteile: Er spart Zeit für die Erstellung von Threads (wenige Threads können Hunderte von Anfragen bearbeiten), und durch die Begrenzung der Thread-Anzahl verhindert er, dass die Anwendung von zu vielen Anfragen überlastet wird.

    Ein Executor wird über seine Methode [shutdown] beendet (er nimmt keine neuen Aufgaben mehr an, und seine Threads enden, sobald die bereits eingereichten Aufgaben abgeschlossen sind), gegebenenfalls gefolgt von [awaitTermination] (die auf das Ende der Aufgaben wartet), oder über [shutdownNow] (die die laufenden Aufgaben unterbricht). Ab Java 19 erweitert [ExecutorService] die Schnittstelle [AutoCloseable]: Ihre Methode [close] ruft [shutdown] auf und wartet dann auf das Ende aller Aufgaben. In Kotlin können Sie einen Executor daher in einem Block [use { … }] verwenden – der Erweiterungsfunktion von [AutoCloseable] , die die Anweisung [try] mit einer Java-Ressource ersetzt (Kapitel 3) –. package threads25

import java.time.Duration
import java.time.LocalTime
import java.time.format.DateTimeFormatter
import java.util.concurrent.ArrayBlockingQueue
import java.util.concurrent.RejectedExecutionException
import java.util.concurrent.ThreadPoolExecutor
import java.util.concurrent.TimeUnit

// die an jeden Job übergebene Information
data class Data(val number: Int, val start: LocalTime, val duration: Int)

fun main() {
    Thread.currentThread().name = "Main"
    // 3 permanente Threads, höchstens 5 Threads, eine Warteschlange mit 2 Jobs
    ThreadPoolExecutor(3, 5, 60, TimeUnit.SECONDS, ArrayBlockingQueue(2)).use { pool ->
        // 8 Jobs von 3 s werden an den Pool übergeben
        for (i in 0..<8) {
            val data = Data(i, LocalTime.now(), 3)
            try {
                pool.execute { sleep(data, pool) }
            } catch (_: RejectedExecutionException) {
                println("${time()} : job no. $i was rejected by the pool")
            }
        }
        println("${time()} : thread Main handed the jobs to the pool and waits for their end")
        // das Ende des use-Blocks schließt den Pool: close() wartet auf das Ende der übermittelten Jobs
    }
    println("${time()} : end of thread Main")
}

// der von einem Pool-Thread ausgeführte Job
fun sleep(data: Data, pool: ThreadPoolExecutor) {
    // Zustand des Pools
    val name = Thread.currentThread().name
    println("${time()} : job no. ${data.number} starts in thread $name" +
            " (threads: ${pool.poolSize}, active: ${pool.activeCount}, queued: ${pool.queue.size})")
    // [duration] Sekunden schlafen
    try {
        Thread.sleep(data.duration * 1000L)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
    val duration = Duration.between(data.start, LocalTime.now()).toMillis() / 1000.0
    println("%s : job no. %d ends: scheduled for %d s, it lasted %.2f s since it was requested"
            .format(time(), data.number, data.duration, duration))
}

    8.11. Datenparallelität

    8.11.1. Parallele Streams

    Kehren wir zur Hauptverwendung von Threads zurück: alle Prozessoren für eine zeitaufwendige Berechnung zu nutzen. // ein Task, der die Primzahlen des Intervalls [start, end[ zählt
class CountPrimes(private val start: Int, private val end: Int) : RecursiveTask<Int>() {
    companion object {
        // unterhalb dieser Schwelle wird das Teilstück direkt verarbeitet
        const val THRESHOLD = 100_000
        // die Anzahl der von jedem Thread verarbeiteten Teilstücke
        val chunks = ConcurrentHashMap<String, Int>()
    }

    override fun compute(): Int {
        // Teilstück klein genug: es wird sequentiell verarbeitet
        if (end - start <= THRESHOLD) {
            chunks.merge(Thread.currentThread().name, 1, Int::plus)
            return (start..<end).count { isPrime(it) }
        }
        // andernfalls wird es in zwei Hälften geteilt
        val middle = (start + end) ushr 1
        val left = CountPrimes(start, middle)
        val right = CountPrimes(middle, end)
        // die linke Hälfte wird an den Pool übergeben (ein anderer Thread kann sie "stehlen")
        left.fork()
        // die rechte Hälfte wird vom aktuellen Thread verarbeitet
        val nbRight = right.compute()
        // wir warten auf das Ergebnis der linken Hälfte und kombinieren die beiden Ergebnisse
        return left.join() + nbRight
    }
}

    8.12. Thread-lokale Daten

    8.12.1. Das Prinzip

    Betrachten wir eine Drei-Schichten-Anwendung:

    Nehmen wir an, die Anwendung ist mehrbenutzerfähig, etwa eine Webanwendung. Jede Benutzeranfrage wird von einem Thread bearbeitet. Der Lebenszyklus des Threads ist wie folgt:

    • Der Thread wird erstellt (virtueller Thread) oder aus einem Thread-Pool angefordert, um die Anfrage eines Benutzers zu bearbeiten;
    • Benötigt diese Anfrage Daten, führt der Thread eine Funktion der Schicht [ui] aus, die eine Funktion der Schicht [business] aufruft, die ihrerseits eine Funktion der Schicht [dao] aufruft;
    • Der Thread gibt dem Benutzer die Antwort zurück. Anschließend wird er entweder beendet oder an den Thread-Pool zurückgegeben.

    Im zweiten Schritt kann es nützlich sein, dass der Thread über eigene Daten verfügt – also Daten, die nicht mit anderen Threads geteilt werden. Diese Daten könnten zum Beispiel dem Benutzer gehören, den der Thread gerade bedient, und in den verschiedenen Schichten [ui, business, dao] verwendet werden, ohne jeder Funktion als Parameter übergeben zu werden.

    Das JDK stellt hierfür zwei Werkzeuge bereit, die Kotlin unverändert verwendet:

    • die Klasse [ThreadLocal<T>] (Java 1.2): ein Objekt, dessen Wert – gelesen mit [get()] und geschrieben mit [set(value)] – für jeden Thread verschieden ist. Der Konstruktor [ThreadLocal.withInitial(factory)] liefert den Anfangswert für jeden Thread; die Methode [remove()] löscht den Wert des aktuellen Threads. Die abgeleitete Klasse [InheritableThreadLocal<T>] gibt den Wert des erzeugenden Threads an den neu erzeugten Thread weiter;
    • die Klasse [ScopedValue<T>] (final in Java 25): ein Wert, der für einen begrenzten Codebereich an einen Thread gebunden ist und innerhalb dieses Bereichs nicht verändert werden kann.

    8.12.3. Die Klasse ScopedValue

    Ein Wert [ScopedValue<T>] wird gebunden an einen Wert für die Ausführung eines Codeabschnitts, seinen Gültigkeitsbereich (Scope):

    • [ScopedValue.newInstance()] erzeugt einen gebundenen Wert, der typischerweise in einer Property auf oberster Ebene oder in der Property eines Objekts gespeichert wird und schreibgeschützt ist ([val]);
    • [ScopedValue.where(sv, value).run(action)] führt die Aktion (ein [Runnable]) aus und bindet dabei [sv] an [value]. Solange die Aktion – und alle Funktionen, die sie aufruft – im aktuellen Thread ausgeführt wird, [sv.get()] liefert [value]. Wenn die Aktion endet, verschwindet die Bindung: Es gibt nichts aufzuräumen;
    • [ScopedValue.where(sv, value).call(op)] führt dasselbe mit einer Operation aus, die ein Ergebnis zurückgibt;
    • innerhalb des Gültigkeitsbereichs kann der Wert nicht verändert werden; er kann nur für einen verschachtelten Bereich an einen anderen Wert gebunden werden;
    • [isBound()] gibt an, ob der Wert im aktuellen Thread gebunden ist (Kotlin behandelt dies als Eigenschaft [isBound]); [orElse(other)] liefert den gebundenen Wert oder, falls keiner gebunden ist, [other]. Außerhalb jedes Bereichs [get()] löst die Ausnahme [NoSuchElementException] aus.

    • nur die Basisoperationen (Einfügen, Ändern, Löschen, Lesen eines Artikels) in die Schicht [dao] aufnehmen;
    • Operationen, die mehrere Artikel gleichzeitig aktualisieren, in die Schicht [business] verlagern. Diese Operationen verwenden die Basisoperationen der Schicht [dao].

    Der Vorteil dieser Lösung ist, dass dieselbe Schicht [dao] ohne Änderung mit verschiedenen Schichten [business] verwendet werden kann. Sie bringt jedoch eine Herausforderung bei der Verwaltung der Transaktion mit sich, die die atomar auszuführenden Aktualisierungen zusammenfasst:

    • Die Transaktion muss von der Schicht [business] gestartet werden, bevor diese die Funktionen der Schicht [dao] aufruft;
    • die Funktionen der Schicht [dao] müssen von der Existenz der Transaktion wissen, um daran teilnehmen zu können;
    • die Transaktion muss von der Schicht [business] abgeschlossen werden (Commit oder Rollback).

    Damit die Funktionen der Schicht [dao] von einer laufenden Transaktion wissen, könnte man die Transaktion jeder Funktion der Schicht [dao] als Parameter übergeben. Dieser Parameter würde dann in der Signatur der Schnittstellenfunktionen erscheinen und die Schnittstelle damit an eine bestimmte Datenquelle binden. Threadlokale Daten bieten eine elegantere Lösung: Die Schicht [business] legt die Transaktion in den threadlokalen Daten ab, und dort ruft die Schicht [dao] sie ab. Die Funktionssignaturen der Schicht [dao] müssen nicht geändert werden. Mehrere Threads (mehrere Benutzer) können gleichzeitig arbeiten: Jeder hat seine eigene Transaktion.

class Transaction {
    companion object {
        private val counter = AtomicInteger()
    }

    private val undos = ArrayDeque<() -> Unit>()
    val number = counter.incrementAndGet()

    // speichert die Operation, die eine Aktualisierung rückgängig macht
    fun log(undo: () -> Unit) {
        undos.addFirst(undo)
    }

    // bestätigt die Transaktion: die Aktualisierungen bleiben erhalten
    fun commit() {
        undos.clear()
    }

    // setzt die Transaktion zurück: die Aktualisierungen werden rückgängig gemacht, von der letzten bis zur ersten
    fun rollback() {
        while (true) {
            val undo = undos.removeFirstOrNull() ?: break
            undo()
        }
    }
}

interface IDao {
    fun insertArticle(article: Article): Int
    fun getAllArticles(): List<Article>
    fun deleteAllArticles()
}

class Dao : IDao {
    // die Tabelle, von allen Threads gemeinsam genutzt, und ihr Lock
    private val table = mutableListOf<Article>()
    private val lock = Any()
    private var nextId = 1

    override fun insertArticle(article: Article): Int {
        // läuft im aktuellen Thread eine Transaktion?
        val transaction = ThreadContext.transaction.get()
        synchronized(lock) {
            check(table.none { it.name == article.name }) { "an article named [${article.name}] already exists" }
            val inserted = article.copy(id = nextId++)
            table += inserted
            // in einer Transaktion merken wir uns, wie das Einfügen rückgängig gemacht wird
            transaction?.log {
                synchronized(lock) { table -= inserted }
            }
            val mode = if (transaction == null) "outside a transaction"
                       else "in transaction ${transaction.number}"
            val name = Thread.currentThread().name
            println("[$name] [dao] insertion of ${inserted.name} (id ${inserted.id}) $mode")
            return 1
        }
    }

    override fun getAllArticles(): List<Article> = synchronized(lock) { table.toList() }

    override fun deleteAllArticles() {
        synchronized(lock) { table.clear() }
    }
}

    • Zeile 16: Die Funktion [insertArticle] ruft eine eventuell von der Schicht [business] in den lokalen Daten des aktuellen Threads abgelegte Transaktion ab. Ihre Variable [transaction] hat den Typ [Transaction?];
    • Zeile 18: Die Tabelle hat eine Eindeutigkeitsbedingung für Artikelnamen: Das Einfügen eines Artikels mit einem bereits vorhandenen Namen löst eine Ausnahme aus. Die Kotlin-Funktion [check] (Kapitel 3) löst eine [IllegalStateException] aus, mit der vom Lambda berechneten Meldung, wenn die Bedingung falsch ist; die Funktion [none] prüft, dass kein Element der Tabelle das Prädikat erfüllt;
    • Zeilen 19–20: Der eingefügte Datensatz ist eine Kopie des empfangenen Datensatzes, mit einer von der Schicht [dao] vergebenen Kennung. Da eine schreibgeschützte Datenklasse nicht verändert werden kann, wird mit der Funktion [copy] ein neues Objekt erzeugt, das nur die benannte Eigenschaft ändert;
    • Zeilen 22–23: Wenn es eine Transaktion gibt, nimmt die Schicht [dao] daran teil, indem sie festhält, wie das Einfügen rückgängig gemacht wird. Der sichere Aufruf [?.] ruft [log] nur auf, wenn [transaction] ungleich [null] ist. Das Rollback-Lambda, das als abschließendes Lambda übergeben wird, erfasst die Variable [inserted];
    • Zeilen 25–28: Eine Trace-Ausgabe zeigt den Thread, den eingefügten Datensatz und eine eventuelle Transaktion. Im Zweig [else] weiß der Compiler, dass [transaction] nicht [null] ist (Smart Cast);

    // die [business]-Schicht
interface IBusiness {
    fun insertArticlesInTransaction(articles: List<Article>)
    fun insertArticlesOutOfTransaction(articles: List<Article>)
    fun getAllArticles(): List<Article>
    fun deleteAllArticles()
}

class Business(private val dao: IDao) : IBusiness {
    // Einfügen einer Liste von Artikeln: alles oder nichts
    override fun insertArticlesInTransaction(articles: List<Article>) {
        val name = Thread.currentThread().name
        // Beginn der Transaktion, in den threadlokalen Daten gespeichert
        val transaction = Transaction()
        ThreadContext.transaction.set(transaction)
        try {
            for (article in articles) {
                // die [dao]-Schicht findet die Transaktion im Thread
                dao.insertArticle(article)
                // simulierte Verarbeitung, die anderen Threads Zeit zum Eingreifen gibt
                sleep(200)
            }
            transaction.commit()
            println("[$name] [business] transaction ${transaction.number} committed")
        } catch (e: RuntimeException) {
            transaction.rollback()
            println("[$name] [business] transaction ${transaction.number} rolled back")
            // die Exception wird an den Aufrufer weitergeworfen
            throw e
        } finally {
            // der Thread hat keine laufende Transaktion mehr
            ThreadContext.transaction.remove()
        }
    }

    // Einfügen einer Liste von Artikeln ohne Transaktion
    override fun insertArticlesOutOfTransaction(articles: List<Article>) {
        articles.forEach(dao::insertArticle)
    }

    override fun getAllArticles(): List<Article> = dao.getAllArticles()

    override fun deleteAllArticles() = dao.deleteAllArticles()
}
    • Zeile 9: Die Schicht [dao] wird durch den primären Konstruktor injiziert, wodurch sie zu einer privaten Eigenschaft wird;
    • Zeilen 14–15: Die Funktion [insertArticlesInTransaction] startet eine Transaktion und speichert sie in den lokalen Daten des Threads;
    • Zeile 19: Die Einfügefunktion der Schicht [dao] wird für jeden Artikel aufgerufen, ohne dass ihr die Transaktion übergeben wird;
    • Zeile 21: Eine Pause simuliert eine Verarbeitung, damit ein anderer Thread Zeit hat, während der Transaktion einzugreifen (dritter Teil des Testprogramms);
    • Zeile 23: Wenn das Programm diesen Punkt erreicht, ist keine Ausnahme aufgetreten: Die Transaktion wird bestätigt (Commit);
    • Zeilen 25–29: Wenn eine Ausnahme auftritt, wird die Transaktion zurückgerollt, und die Ausnahme wird erneut an den Aufrufer ausgelöst;
    • Zeile 32: In jedem Fall hat der Thread danach keine aktive Transaktion mehr: [remove()] löscht den Wert des Threads. Das ist unerlässlich, wenn der Thread wiederverwendet wird (ein Thread aus einem Pool);
    • Zeilen 37–38: dasselbe Einfügen ohne Transaktion. Die gebundene Referenz [dao::insertArticle] verweist auf die Funktion [insertArticle] des Objekts [dao];
    • Die letzten beiden Funktionen delegieren ihre Arbeit an die Schicht [dao], mit einem auf einen einzigen Ausdruck reduzierten Rumpf.

    business.deleteAllArticles()

    val threadA = thread(name = "A") { execute { business.insertArticlesInTransaction(articlesA) } }
    Thread.sleep(100)

    threadA.join()

// führt eine Aktion aus und zeigt gegebenenfalls die Exception an
fun execute(action: () -> Unit) {
    try {
        action()
    } catch (e: RuntimeException) {
        println("[${Thread.currentThread().name}] ${e::class.simpleName} : ${e.message}")
    }
}

// [ms] Millisekunden schlafen
fun sleep(ms: Long) {
    try {
        Thread.sleep(ms)
    } catch (_: InterruptedException) {
        Thread.currentThread().interrupt()
    }
}

// zeigt die Liste der Artikel an
fun displayArticles(business: IBusiness) {
    println("List of articles:")
    for (article in business.getAllArticles()) {
        println("  $article")
    }
}

    8.12.5. Fazit

    Das vorangegangene Beispiel hat den Nutzen threadlokaler Daten für die Transaktionsverwaltung gezeigt. Es sollte nicht genau so nachgebaut werden, beschreibt aber zutreffend die Funktionsweise von Frameworks: Die Transaktionsverwaltung von Spring (Annotation [@Transactional]) legt die Transaktion und die Datenbankverbindung in einem [ThreadLocal] ab, das die Datenzugriffsschichten abfragen, ohne dass ihr Code die Transaktion handhaben muss; Hibernate kann die Arbeitssitzung ähnlich dem aktuellen Thread zuordnen. Wir kommen in Kapitel 11 auf diese Werkzeuge zurück. In neuem Code, insbesondere mit virtuellen Threads, ist ein *[ScopedValue]* der empfohlene Weg, solche Kontextinformationen weiterzureichen; bei Coroutinen übernimmt der Coroutine-Kontext diese Rolle (Kapitel 9).

    Die Thread-Synchronisation ist ein anspruchsvolles Gebiet. Dieses Kapitel hat die wichtigsten Werkzeuge vorgestellt; zum Weiterlesen:

    • das Buch von Brian Goetz et al., [Java Concurrency in Practice] (Addison-Wesley), das trotz seiner Entstehung vor den virtuellen Threads weiterhin das maßgebliche Referenzwerk zum Thema ist. Seine Beispiele sind in Java, aber alles, was es sagt, gilt auch für Kotlin auf der JVM;
    • der Abschnitt „Concurrency“ des Java-Tutorials von Oracle: Lesson: Concurrency – er ist alt, aber für die Grundlagen weiterhin zutreffend;
    • die Dokumentation des Pakets [java.util.concurrent]: Package java.util.concurrent, deren Abschnitt „Memory Consistency Properties“ die „Happens-before“-Beziehungen zusammenfasst;
    • die Dokumentation des Pakets [kotlin.concurrent] der Kotlin-Standardbibliothek ([thread], [withLock], [read], [write], [getOrSet] …): kotlin.concurrent;
    • die Java Enhancement Proposals (JEP), die virtuelle Threads und Scoped Values eingeführt haben: JEP 444: Virtual Threads und JEP 506: Scoped Values.

    In modernem Code werden Objekte ([Thread]) nur selten direkt manipuliert. In Java verwendet man bevorzugt Executors ([ExecutorService]), parallele Streams für Berechnungen und virtuelle Threads für Aufgaben, die mit Warten verbunden sind. Kotlin besitzt all diese Werkzeuge, bietet aber eine eigene Lösung, die im nächsten Kapitel vorgestellt wird: Coroutinen. Eine Coroutine ist eine Aufgabe, die sich selbst suspendieren kann (bei Netzwerk-, Datenbank- oder Dateizugriffen), ohne den ausführenden Thread zu blockieren, und danach fortgesetzt wird, gegebenenfalls in einem anderen Thread; die strukturierte Nebenläufigkeit stellt sicher, dass keine Coroutine vergessen wird und dass Fehler und Abbrüche korrekt weitergegeben werden. Die Konzepte dieses Kapitels bleiben dennoch unverzichtbar: Coroutinen laufen in Threads, und die Daten, die sie gemeinsam nutzen, müssen mit denselben Werkzeugen geschützt werden (Sperren, atomare Klassen, nebenläufige Collections) oder mit deren Entsprechungen für Coroutinen ([Mutex], [Channel] …).
