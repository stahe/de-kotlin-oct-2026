    7. Funktionstypen, Lambdas und Ereignisse

    In vielen Programmen müssen wir einer Funktion nicht Daten, sondern Verhalten übergeben: das Sortierkriterium, die Filterbedingung oder die Aktion, die bei einem Ereignis ausgeführt werden soll. Kotlin begegnet diesem Bedarf, indem es Funktionen wie jeden anderen Wert behandelt: Eine Funktion hat einen Typ – den Funktionstyp, der beispielsweise als [(Int, Int) -> Int] notiert wird. Sie kann in einer Variablen gespeichert, als Parameter übergeben, als Ergebnis einer anderen Funktion zurückgegeben und jederzeit ausgeführt werden. Eine Funktion, die eine Funktion annimmt oder zurückgibt, heißt Funktion höherer Ordnung.

    Java besitzt bekanntlich keine Funktionstypen: Es stützt sich auf funktionale Schnittstellen – Schnittstellen mit genau einer abstrakten Methode ([Runnable], [Comparator], [Function<T, R>]…) – und erlaubte erst mit Java 8 (2014), sie mit Lambda-Ausdrücken und Methodenreferenzen zu implementieren. Kotlin unterstützt Lambdas seit seiner allerersten Version und kann auch mit den funktionalen Schnittstellen von Java arbeiten, da es Java-Bibliotheken direkt verwendet. Wir haben Lambdas bereits ausgiebig genutzt, ohne ins Detail zu gehen, nämlich bei den Collection-Operationen aus Kapitel 5: In [persons.filter { it.age >= 18 }] übergeben wir der Funktion [filter] ein Lambda. Dieses Kapitel erklärt, was hinter dieser Syntax steckt. Es schließt mit den Ereignissen, die Kotlin – wie Java – über „Listener“ behandelt: Funktionen, meist Lambdas, die sich bei einem Sender registrieren, um über dortige Vorgänge benachrichtigt zu werden. Grafische Benutzeroberflächen (Swing, JavaFX, Compose) und Web-Frameworks stützen sich gleichermaßen auf diesen Mechanismus: Ein Klick auf eine Schaltfläche oder das Eintreffen einer HTTP-Anfrage wird den registrierten Listenern signalisiert. Dieser Kurs behandelt keine grafischen Benutzeroberflächen; alle Beispiele sind Konsolenprogramme.

    Die Programme dieses Kapitels sind im Gradle-Projekt [07-lambdas] organisiert, mit einem Paket pro Programm: [src/main/kotlin/lambdas01/Lambdas01.kt], [src/main/kotlin/lambdas02/Lambdas02.kt]… Sie werden mit [gradlew -q run -Pmain=lambdas01.Lambdas01Kt] oder per Klick auf das grüne Dreieck in IntelliJ oder IDEA ausgeführt. Das Projekt benötigt keine weiteren Bibliotheken als die Kotlin-Standardbibliothek: Funktionstypen, Lambdas und Scope-Funktionen sind enthalten, und die Schnittstellen des Pakets [java.util.function] sind dieselben wie im JDK.

    7.1. Funktionstypen und vordefinierte funktionale Schnittstellen

    7.1.1. Das Konzept des Funktionstyps

    Ein Funktionstyp beschreibt ein Muster (auch Signatur oder Form genannt) einer Funktion: die Typen ihrer Parameter in Klammern, gefolgt von einem Pfeil und dem Typ ihres Rückgabewerts. Eine Variable eines Funktionstyps kann auf jede Funktion dieser Form verweisen und sie ausführen. Hier einige Beispiele:

    • [() -> Unit]: eine Funktion ohne Parameter, die kein nützliches Ergebnis zurückgibt ([Unit] übernimmt die Rolle von [void] in Java);
    • [() -> String]: eine Funktion ohne Parameter, die eine Zeichenkette zurückgibt;
    • [(Int) -> Boolean]: eine Funktion, die eine ganze Zahl annimmt und einen booleschen Wert zurückgibt, mit anderen Worten ein Prädikat;
    • [(Int, Int) -> Int]: eine Funktion, die zwei ganze Zahlen annimmt und eine ganze Zahl zurückgibt;
    • [(String) -> (Int) -> Int]: eine Funktion, die eine Zeichenkette annimmt und … eine Funktion vom Typ [(Int) -> Int] zurückgibt (der Pfeil wird von rechts nach links gelesen);
    • [(() -> Unit)?]: eine Funktion, die fehlen kann; die Klammern sind notwendig, da [() -> Unit?] andernfalls eine Funktion bezeichnen würde, die einen [Unit?] zurückgibt. Hier zeigt sich die Null-Sicherheit in Bezug auf [null] aus Kapitel 3: Eine solche Funktion wird mit [f?.invoke()] aufgerufen;
    • [String.(Int) -> String]: eine Funktion mit Empfänger; sie wird – wie eine Erweiterungsfunktion (Kapitel 4) – auf eine Zeichenkette angewendet, die ihr Code als [this] bezeichnet. Sie kann als Erweiterung aufgerufen werden (["ab".f(3)]) oder als gewöhnliche Funktion, deren erster Parameter der Empfänger ist ([f("ab", 3)]).

    Parameter können benannt werden, um den Typ zu dokumentieren: [(n1: Int, n2: Int) -> Int] ist derselbe Typ wie [(Int, Int) -> Int].

    Es gibt drei Möglichkeiten, einen Wert eines Funktionstyps zu erhalten:

    • eine Referenz auf eine bestehende Funktion schreiben, die die richtige Form hat: [val task: () -> Unit = ::display];
    • einen Lambda-Ausdruck schreiben: [val task: () -> Unit = { println("task") }];
    • eine anonyme Funktion schreiben: [val task = fun() { println("task") }], oder ein Objekt einer Klasse, die den Funktionstyp implementiert (ein Funktionstyp ist, wie wir sehen werden, eine Schnittstelle). Diese beiden Schreibweisen sind weniger gebräuchlich.

    Die Funktion wird dann wie eine gewöhnliche Funktion ausgeführt: [task()]. Das ist eine Kurzschreibweise für den Aufruf der Methode [invoke] des Funktionsobjekts: [task.invoke()]. Das ist der erste spürbare Unterschied zu Java, wo Sie die Methode der Schnittstelle mit ihrem Namen aufrufen müssen ([run], [apply], [test]…); Kotlin verhält sich hier wie C#, wo ein Delegate wie eine Methode aufgerufen wird.

    7.1.2. Funktionstypen von Kotlin und Schnittstellen aus java.util.function

    Vor Java 8 definierte jede Java-Bibliothek ihre eigenen Schnittstellen mit einer einzigen Methode ([Runnable], [Comparator], [ActionListener]…). Java 8 führte das Paket [java.util.function] ein, das 43 generische funktionale Schnittstellen bereitstellt. Kotlin braucht sie nicht: Ein Funktionstyp wird direkt geschrieben. Diese Schnittstellen lassen sich jedoch weiterhin von Kotlin aus verwenden, und Sie werden ihnen bei jedem Aufruf einer Java-Bibliothek begegnen. Die folgende Tabelle ordnet die wichtigsten Java-Schnittstellen den Funktionstypen von Kotlin zu:

    Die Java-Versionen für primitive Typen

    In Kotlin gibt es keine praktische Begrenzung der Parameteranzahl eines Funktionstyps: [(Int, Int, Int) -> Int] wird ebenso einfach geschrieben wie die anderen, während Sie in Java, da es keine vordefinierte Schnittstelle mit drei Parametern gibt, eine eigene definieren müssen.

    Wie stellt die Java Virtual Machine, die nur Klassen und Schnittstellen kennt, einen Funktionstyp dar? Über generische Schnittstellen der Kotlin-Bibliothek: [kotlin.jvm.functions.Function0<R>], [Function1<P1, R>], [Function2<P1, P2, R>]… bis hin zu [Function22], danach folgt eine Schnittstelle [FunctionN] . Jede hat eine einzige Methode, [invoke]: [(Int, Int) -> Int] wird zu [Function2<Integer, Integer, Integer>] kompiliert, deren Methode [operator fun invoke(p1: Int, p2: Int): Int] ist. Der Modifikator [operator] von [invoke] (siehe Operatorüberladung in Kapitel 4) ermöglicht die Schreibweise [f(2, 3)]. Ein Funktionstyp ist für die JVM also eine funktionale Schnittstelle wie die von Java. Da Java-Generics nur für Objekttypen gelten, werden [Int]-Werte, die an einen [(Int, Int) -> Int] übergeben werden, in [Integer] umgewandelt und umgekehrt (Boxing und Unboxing). Java vermeidet diese Umwandlungen durch seine spezialisierten Schnittstellen ([IntBinaryOperator]…); Kotlin vermeidet sie auf andere Weise, mit den [inline]-Funktionen, auf die wir später eingehen.

import java.util.function.IntBinaryOperator
import java.util.function.Predicate

// Kotlin-Funktionstypen und funktionale Java-Interfaces

fun main() {
    // 1 - () -> Unit: kein Parameter, kein Ergebnis
    val task: () -> Unit = ::display
    // Ausführung: die Funktion wird wie eine gewöhnliche Funktion aufgerufen
    task()
    // was eine Kurzform für den Aufruf ihrer Methode invoke ist
    task.invoke()

    // 2 - (Int, Int) -> Int: zwei Parameter, ein Ergebnis
    val operation: (Int, Int) -> Int = ::add
    println("operation(2, 3)=${operation(2, 3)}")
    // () -> String: kein Parameter, ein Ergebnis
    val greet: () -> String = ::greet
    println("greet()=${greet()}")

    // 3 - (String) -> Unit: ein Parameter, kein Ergebnis
    val write: (String) -> Unit = ::println
    write("(String) -> Unit executed println")

    // 4 - (Int) -> Boolean: ein Prädikat
    val isEven: (Int) -> Boolean = ::isEven
    println("isEven(8)=${isEven(8)}")
    val numbers = mutableListOf(3, 8, 1, 6, 5, 4)
    // removeAll aus der Kotlin-Bibliothek erwartet ein (Int) -> Boolean
    val modified = numbers.removeAll(isEven)
    println("even numbers removed: $modified, remaining: $numbers")

    // 5 - ein Comparator<T> (Java-Interface), erstellt aus einer Funktion (SAM-Konvertierung)
    val names = mutableListOf("Paul", "Mélanie", "Jo", "Sébastien")
    names.sortWith(Comparator(::compareLengths))
    println("sorted by length: $names")

    // 6 - die Interfaces aus java.util.function bleiben verwendbar
    val supplier: Supplier<String> = Supplier(::greet)
    val multiply = IntBinaryOperator(::multiply)
    val predicate = Predicate<Int> { it > 4 }
    println("supplier.get()=${supplier.get()}")
    println("multiply.applyAsInt(2, 3)=${multiply.applyAsInt(2, 3)}")
    // removeIf ist eine Java-Methode (Collection): sie erwartet ein Predicate
    val values = mutableListOf(10, 3, 8, 7, 2, 1)
    values.removeIf(predicate)
    // eine Kotlin-Funktion wird automatisch in ein Predicate konvertiert (SAM-Konvertierung)
    values.removeIf(isEven)
    values.removeIf { it == 1 }
    println("after removeIf: $values")

    // 7 - ein nullable Funktionstyp: die Funktion kann fehlen
    execute(null)
    execute(task)

    // 8 - ein Funktionstyp mit Receiver: String.(Int) -> String
    val times: String.(Int) -> String = String::repeat
    println("\"ab\".times(3)=${"ab".times(3)}, times(\"cd\", 2)=${times("cd", 2)}")

    // 9 - eine Funktion ist ein Objekt, eine Instanz einer Klasse, die ein Interface implementiert
    println("class: ${operation::class.java.name}")
    println("interfaces: ${operation::class.java.interfaces.contentToString()}")
    val sum: (Int, Int) -> Int = { n1, n2 -> n1 + n2 }
    println("class of the lambda: ${sum::class.java.name}")
    println("interfaces: ${sum::class.java.interfaces.contentToString()}")
}

// eine Funktion, die eine möglicherweise fehlende Funktion erhält

    // sicherer Aufruf: nichts wird ausgeführt, wenn callback null ist
    callback?.invoke()
    println("callback ${if (callback == null) "absent" else "present"}")
}

    7.2. Eigene Funktionstypen definieren

    Funktionstypen reichen oft aus, doch möchte man einem Funktionsmuster manchmal einen Namen geben. Kotlin bietet dafür zwei Werkzeuge, die sich ihrer Natur nach stark unterscheiden.

    Das erste ist ein Typalias, das mit dem Schlüsselwort [typealias] deklariert wird:

    • [typealias BinaryOperation = (n1: Int, n2: Int) -> Int]

    Ein Alias erzeugt keinen neuen Typ: [BinaryOperation] ist ein anderer Name für [(Int, Int) -> Int], und beide Schreibweisen sind austauschbar. Der Alias macht den Code lesbarer, wenn der Funktionstyp lang ist oder häufig vorkommt.

    Das zweite ist die funktionale Schnittstelle, die mit [fun interface] deklariert wird:

    • [fun interface Operation { fun calculate(n1: Int, n2: Int): Int }]

    Dies ist das exakte Äquivalent einer funktionalen Java-Schnittstelle: eine Schnittstelle mit nur einer abstrakten Methode (auch SAM oder „Single Abstract Method“-Schnittstelle genannt). Sie darf auch Methoden mit Rumpf und nicht abstrakte Eigenschaften haben; diese zählen nicht. Das Schlüsselwort [fun] vor [interface] erfüllt denselben Zweck wie die Java-Annotation [@FunctionalInterface], mit einem wichtigen Unterschied: Es ist nicht optional. Dieses Schlüsselwort ermöglicht die SAM-Konvertierung – also die Erzeugung eines [Operation]-Objekts aus einem Lambda oder einer Funktionsreferenz: [Operation { n1, n2 -> n1 + n2 }]. Ohne das Schlüsselwort [fun] kann eine Kotlin-Schnittstelle – selbst wenn sie nur eine einzige Methode hat – nur von einer Klasse oder einem anonymen Objekt implementiert werden ([object : Operation { … }]).

    Im Vergleich zum Typ [(Int, Int) -> Int] ist der Typ [Operation] ein wirklich neuer Typ, der sich von allen anderen unterscheidet: Er hat einen Namen, der seinen Zweck beschreibt, seine Methode hat einen aussagekräftigen Namen ([calculate] statt [invoke]), er kann zusätzliche Methoden haben, und er kann von einer benannten Klasse implementiert werden. Umgekehrt wird er über seinen Methodennamen ausgeführt ([op.calculate(2, 3)]), nicht über [op(2, 3)].

    Eine Variable namens [op] vom Typ [Operation], wie eine Variable vom Typ [(Int, Int) -> Int], verweist jeweils auf nur eine Funktion.     n = op.calculate(2, 3)
    println("n=$n")

    // eine Variable referenziert nur eine Funktion: um mehrere auszuführen, verwendet man eine Liste
    val operations = listOf(
        Operation(c1::add),
        Operation(c1::subtract),
        Operation { n1, n2 -> n1 * n2 },
    )
    for (operation in operations) {
        println("-> ${operation.calculate(10, 4)}")
    }

    // eine Methode des Interfaces erstellt eine neue Operation
    val squaredSum = Operation(c1::add).then { x -> x * x }
    println("squaredSum.calculate(1, 2)=${squaredSum.calculate(1, 2)}")

    // Operation und IntBinaryOperator haben dieselbe Form, sind aber zwei verschiedene Typen
    val other = IntBinaryOperator(op::calculate)
    println("other.applyAsInt(5, 1)=${other.applyAsInt(5, 1)}")

    // ein generisches funktionales Interface
    val length = Transformation(String::length)
    val stars = Transformation("*"::repeat)
    println("length(\"Hello\")=${length.transform("Hello")}")
    println("stars(5)=${stars.transform(5)}")

    // ein Typalias: einfach ein anderer Name für (Int, Int) -> Int
    val f: BinaryOperation = { n1, n2 -> n1 - n2 }
    // BinaryOperation und (Int, Int) -> Int sind derselbe Typ
    val g: (Int, Int) -> Int = f
    // aber Operation ist ein anderer Typ: eine Konvertierung ist nötig
    val op2 = Operation(g)
    println("f(5, 1)=${f(5, 1)}, g(5, 1)=${g(5, 1)}, op2.calculate(5, 1)=${op2.calculate(5, 1)}")

// Definition eines funktionalen Interfaces: eine einzige abstrakte Methode
// mit zwei Ganzzahlen als Parametern und einer Ganzzahl als Rückgabewert
fun interface Operation {
    fun calculate(n1: Int, n2: Int): Int

    // eine Methode mit Rumpf zählt nicht: das Interface bleibt funktional
    fun then(next: (Int) -> Int): Operation = Operation { n1, n2 -> next(calculate(n1, n2)) }
}

// ein generisches funktionales Interface: T -> R
fun interface Transformation<T, R> {
    fun transform(value: T): R
}

// von anonymen Objekten zu Lambda-Ausdrücken

fun main() {
    // 1 - ein anonymes Objekt: die Klasse, die den Funktionstyp implementiert, wird an Ort und Stelle geschrieben
    val add = object : (Int, Int) -> Int {
        override fun invoke(n1: Int, n2: Int): Int {
            return n1 + n2
        }
    }
    println("anonymous object: add(2, 3)=${add(2, 3)}")

    // 2 - dasselbe mit einem Lambda-Ausdruck: { Parameter -> Rumpf }
    val subtract = { n1: Int, n2: Int -> n1 - n2 }
    println("lambda with typed parameters: subtract(2, 3)=${subtract(2, 3)}")

    // 3 - die Parametertypen werden aus dem erwarteten Typ abgeleitet
    val multiply: (Int, Int) -> Int = { n1, n2 -> n1 * n2 }
    println("lambda with untyped parameters: multiply(2, 3)=${multiply(2, 3)}")

    // 4 - ein einzelner Parameter: er muss nicht benannt werden und heißt dann it
    val square: (Int) -> Int = { it * it }
    val isEmpty: (String) -> Boolean = { s -> s.isEmpty() }
    println("square(7)=${square(7)}, isEmpty(\"\")=${isEmpty("")}")

    // 5 - kein Parameter: kein Pfeil
    val greet = { "Hello" }
    val beep = { println("beep!") }
    println(greet())
    beep()

    // 6 - ein Rumpf aus mehreren Anweisungen: der Wert des letzten Ausdrucks ist das Ergebnis
    val repeat: (String, Int) -> String = { text, times ->
        val buffer = StringBuilder()
        for (i in 1..times) {
            buffer.append(text)
        }
        buffer.toString()
    }
    println(repeat("ab", 3))

    // 7 - nicht verwendete Parameter: _
    val listener: (Any?, String) -> Unit = { _, _ -> println("event received") }
    listener(null, "click")

    // 8 - ein als Parameter übergebenes Lambda: außerhalb der Klammern, wenn es der letzte Parameter ist
    val numbers = mutableListOf(3, 8, 1, 6, 5, 4)
    val evens = numbers.filter { it % 2 == 0 }
    println("evens: $evens")
    numbers.sortWith { n1, n2 -> n2.compareTo(n1) }
    println("descending order: $numbers")
    // das Lambda außerhalb der Klammern, nach anderen Parametern
    val total = numbers.fold(0) { acc, n -> acc + n }
    println("total: $total")

    // 9 - return in einem Lambda: return@label verlässt nur das Lambda
    numbers.forEach {
        if (it % 2 == 0) return@forEach
        print("$it ")
    }
    println("<- odds")
    // ein vom Entwickler gewähltes Label
    numbers.forEach odd@{ n ->
        if (n % 2 != 0) return@odd
        print("$n ")
    }
    println("<- evens")
    // eine anonyme Funktion: return verlässt dort die anonyme Funktion
    val isLarge = fun(n: Int): Boolean {
        if (n > 5) return true
        return false
    }
    println("large: ${numbers.filter(isLarge)}")

    // 10 - Destrukturierung der Parameter eines Lambdas
    val ages = mapOf("Paul" to 40, "Mélanie" to 35)
    ages.forEach { (name, age) -> println("$name is $age years old") }
}

    • Zeilen 70–74: eine anonyme Funktion. Sie wird wie eine normale Funktion geschrieben, aber ohne Namen. Ihr Typ wird abgeleitet: [(Int) -> Boolean]. In einer anonymen Funktion verlässt [return] die anonyme Funktion selbst. Das wird verwendet, wenn der Rumpf mehrere Austrittspunkte hat oder wenn Sie den Ergebnistyp explizit angeben möchten;

fun main() {
    // 1 - der Typ eines Lambdas wird aus seinen Parametern und seinem Rumpf abgeleitet...
    val double = { x: Int -> x * 2 }
    println("double(21)=${double(21)}")
    // ... oder durch den erwarteten Typ festgelegt: derselbe Lambda-Text kann drei verschiedene Typen ergeben
    val function: () -> String = { "Hello" }
    val supplier = Supplier { "Hello" }
    val callable = Callable { "Hello" }
    println("${function()} / ${supplier.get()} / ${callable.call()}")

    // 2 - die Arten von Referenzen
    // a) Top-Level-Funktion: ::function
    val triple: (Int) -> Int = ::triple
    println("triple(14)=${triple(14)}")
    // b) Methode oder Eigenschaft eines bestimmten Objekts (gebundene Referenz): object::method
    val name = "Pierre"
    val inUpperCase: () -> String = name::uppercase
    val nameLength: () -> Int = name::length
    println("inUpperCase()=${inUpperCase()}, nameLength()=${nameLength()}")
    // c) Methode eines beliebigen Objekts der Klasse (ungebundene Referenz): Class::method
    //    das Objekt, auf dem die Methode aufgerufen wird, wird zum ersten Parameter
    val upperCase: (String) -> String = String::uppercase
    val ignoreCase: (String, String) -> Int = { s1, s2 -> s1.compareTo(s2, ignoreCase = true) }
    println("upperCase(\"paul\")=${upperCase("paul")}")
    println("ignoreCase(\"abc\", \"ABC\")=${ignoreCase("abc", "ABC")}")
    // d) Erweiterungsfunktion: Class::extension
    val convert: (String) -> Int = String::toInt
    println("convert(\"42\") + 1 = ${convert("42") + 1}")
    // e) Konstruktor: ::Class
    val createList: () -> MutableList<String> = ::ArrayList
    val createBuffer: (String) -> StringBuilder = ::StringBuilder
    val createArray: (Int) -> IntArray = ::IntArray
    val createPerson: (String, Int) -> Person = ::Person
    val list = createList()
    list.add("element")
    println("$list ${createBuffer("abc").reverse()} ${createArray(3).size} ${createPerson("Paul", 40)}")

    // 3 - keine geprüften Exceptions: jedes Lambda kann jede Exception werfen
    val read: () -> Int = { throw IOException("file missing") }
    try {
        read()
    } catch (ex: IOException) {
        println("exception received: ${ex.message}")
    }

    // 4 - Gleichheit von Funktionen: Referenzen sind vergleichbar, Lambdas nicht
    val r1: () -> String = name::uppercase
    val r2: () -> String = name::uppercase
    val l1 = { name.uppercase() }
    val l2 = { name.uppercase() }
    println("r1 == r2 : ${r1 == r2}, r1 === r2 : ${r1 === r2}, l1 == l2 : ${l1 == l2}")
}

import java.util.function.Function

// Funktionen komponieren: Funktionen, die Funktionen zurückgeben

fun main() {
    // 1 - Komposition: unsere Erweiterungen then (zuerst this, dann die andere) und after (zuerst die andere)
    val plusOne: (Int) -> Int = { it + 1 }
    val timesTwo: (Int) -> Int = { it * 2 }
    println("(plusOne then timesTwo)(5)=${(plusOne then timesTwo)(5)}")
    println("(plusOne after timesTwo)(5)=${(plusOne after timesTwo)(5)}")
    // die Methoden des Java-Interfaces Function bleiben verfügbar
    val f = Function<Int, Int> { it + 1 }.andThen { it * 2 }
    println("Function.andThen: f.apply(5)=${f.apply(5)}")
    // eine Funktion, die Funktionen erzeugt
    val plusTen = adder(10)
    println("adder(10)(5)=${plusTen(5)}, adder(3)(5)=${adder(3)(5)}")
    // eine aus einer Liste von Funktionen aufgebaute Verarbeitungskette
    val steps: List<(String) -> String> = listOf(String::trim, String::lowercase, { it.replace(' ', '-') })
    val normalize = steps.fold({ s: String -> s }) { function, step -> function then step }
    println("normalize(\"  My Nice Title \")=${normalize("  My Nice Title ")}")

    // 2 - Prädikate: unsere Erweiterungen and, or, not
    val short: (String) -> Boolean = { it.length <= 4 }
    val startsWithP: (String) -> Boolean = { it.startsWith("P") }
    val firstNames = listOf("Paul", "Mélanie", "Jo", "Sébastien", "Pierre")
    println("short and P: ${filterElements(firstNames, short and startsWithP)}")
    println("short or P: ${filterElements(firstNames, short or startsWithP)}")
    println("not short: ${filterElements(firstNames, !short)}")
    // ein Prädikat auf CharSequence eignet sich zum Filtern von Strings
    val notEmpty: (CharSequence) -> Boolean = { it.isNotEmpty() }
    println("not empty: ${filterElements(listOf("a", "", "b"), notEmpty)}")

    // 3 - mehrere Verarbeitungen desselben Werts
    val log = mutableListOf<String>()
    val display: (String) -> Unit = { println("display: $it") }
    val remember: (String) -> Unit = { log.add(it) }
    val both = display andAlso remember
    both("first")
    both("second")
    println("log: $log")

    // 4 - Komparatoren: compareBy, thenBy, thenByDescending, reversed
    val persons = mutableListOf(Person("Paul", 32), Person("Mélanie", 25),
        Person("Jo", 32), Person("Sébastien", 25))
    persons.sortWith(compareBy(Person::age).thenBy(Person::name))
    println("by age then name: $persons")
    persons.sortWith(compareBy(Person::age).reversed().thenByDescending(Person::name))
    println("by descending age then descending name: $persons")
    // mehrere Kriterien gleichzeitig
    persons.sortWith(compareBy({ it.name.length }, { it.name }))
    println("by name length then name: $persons")
    // ein Komparator wird auch verwendet, um das kleinere von zwei Elementen zu wählen
    val byAge = compareBy(Person::age)
    println("younger of Paul and Mélanie: ${minOf(persons[1], persons[2], byAge)}")
}

fun adder(n: Int): (Int) -> Int = { it + n }

// behält die Elemente, die das Prädikat erfüllen
fun <T> filterElements(elements: List<T>, predicate: (T) -> Boolean): List<T> {
    val result = mutableListOf<T>()
    for (element in elements) {
        if (predicate(element)) {
            result.add(element)
        }
    }
    return result
}

    7.4. Inline-Funktionen und Scope-Funktionen

    7.4.1. Inline-Funktionen

    Ein Lambda ist ein Objekt. Die Übergabe eines Lambdas an eine Funktion höherer Ordnung verursacht daher Kosten: die Erzeugung des Objekts (außer bei einem Lambda, das nichts erfasst und das die virtuelle Maschine wiederverwenden kann), der Aufruf seiner Methode [invoke] , die [Int] ↔ [Integer]-Umwandlungen, die die generischen Schnittstellen [Function1], [Function2]… erzwingen, und die [Ref]-Objekte der erfassten Variablen. Bei einer Funktion wie [filter], die für jedes Element von Collections aufgerufen wird, die mitunter sehr groß sein können, fallen diese Kosten ins Gewicht. Kotlin beseitigt sie mit dem Modifikator [inline]: Wird eine Funktion als [inline fun] deklariert, erzeugt der Compiler keinen Aufruf dieser Funktion, sondern kopiert ihren Code an jede Stelle, an der sie aufgerufen wird, und kopiert auch den Code der ihr übergebenen Lambdas. Dadurch gibt es keine Lambda-Objekte, keine [invoke]-Aufrufe und keine Umwandlungen mehr. Die Funktionen der Standardbibliothek, die Lambdas akzeptieren ([forEach], [filter], [map], [fold], [let], [apply], [repeat], [use], [synchronized]…), sind fast alle [inline]. Java hat kein Äquivalent: Es verlässt sich auf den Just-in-Time-Compiler der virtuellen Maschine, um zur Laufzeit ein vergleichbares Ergebnis zu erzielen.

    Das Einfügen des Codes hat eine zweite, auffälligere Folge: Da der Code des Lambdas in die aufrufende Funktion kopiert wird, kann eine unmarkierte [return]-Anweisung von dort aus die aufrufende Funktion verlassen. Das ist der nicht lokale Return , dem wir bei *[forEach] in *[Lambdas03.kt] begegnet sind. Zwei Modifikatoren ergänzen *[inline]*:

    • [noinline], angewendet auf einen Funktionsparameter einer [inline]-Funktion, legt fest, dass das entsprechende Lambda nicht kopiert, sondern als gewöhnliches Objekt übergeben werden soll. Das ist notwendig, wenn die Funktion das Lambda behalten will (in einer Liste speichern, als Ergebnis zurückgeben usw.): Kopierter Code lässt sich nicht in einer Liste speichern;
    • [crossinline] verlangt, dass das Lambda kopiert wird, verbietet aber nicht lokale Returns. Das ist notwendig, wenn die [inline]-Funktion das Lambda nicht selbst ausführt, sondern in einem anderen Kontext – zum Beispiel innerhalb eines von ihr erzeugten [Runnable]-Objekts: Wenn [Runnable] ausgeführt wird, kann die aufrufende Funktion längst beendet sein, und ein [return] könnte sie nicht mehr verlassen.

fun main() {
    // 1 - eine gewöhnliche Funktion erhält ein Funktionsobjekt; eine inline-Funktion erhält den Code des Lambdas
    execute { println("lambda passed to execute, executed by: ${currentMethod()}") }
    executeInline { println("lambda passed to executeInline, executed by: ${currentMethod()}") }

    // 2 - der nicht lokale Return ist nur in einem Lambda erlaubt, das an eine inline-Funktion übergeben wird
    val numbers = listOf(3, 8, 1, 6)
    println("first even of $numbers: ${firstEven(numbers)}")

    // 3 - noinline: ein Lambda, das als Objekt erhalten bleiben muss
    val callbacks = mutableListOf<() -> Unit>()
    executeThenStore(callbacks, { println("executed right away") }, { println("stored callback") })
    println("${callbacks.size} stored callback, which we execute:")
    callbacks.forEach { it() }

    // 4 - crossinline: ein Lambda, das in einem anderen Kontext ausgeführt wird
    val task = asTask { println("executed by ${Thread.currentThread().name}") }
    val thread = Thread(task, "worker")
    thread.start()
    thread.join()

inline fun <T> forEachElement(elements: List<T>, action: (T) -> Unit) {
    for (element in elements) action(element)
}

fun firstEven(numbers: List<Int>): Int? {
    forEachElement(numbers) {
        // nicht lokaler Return: wir verlassen firstEven und nicht nur das Lambda
        if (it % 2 == 0) return it
    }
    return null
}

// immediate wird kopiert; stored bleibt ein Funktionsobjekt, das in die Liste aufgenommen werden kann
inline fun executeThenStore(
    callbacks: MutableList<() -> Unit>,
    immediate: () -> Unit,
    noinline stored: () -> Unit,
) {
    immediate()
    callbacks.add(stored)
}

    7.4.2. Scope-Funktionen

    Die Kotlin-Standardbibliothek stellt fünf kleine, weit verbreitete Funktionen bereit – [inline] – bekannt als „Scope-Funktionen“: [let], [run], [with], [apply] und [also]. Sie tun fast nichts: Jede führt ein Lambda auf einem Objekt aus. Sie unterscheiden sich in zwei Punkten:

    • die Art, wie das Lambda auf das Objekt verweist: entweder als sein Parameter [it] (das Lambda hat den Typ [(T) -> R]) oder als sein Empfänger [this], der dann weggelassen werden kann (das Lambda ist ein Lambda mit Empfänger vom Typ [T.() -> R]; siehe [Lambdas01.kt]);
    • was die Funktion zurückgibt: entweder das Ergebnis des Lambdas oder das Objekt selbst.

// die Scope-Funktionen: let, run, with, apply, also (und takeIf)

fun main() {
    // 1 - apply: konfiguriert das Objekt (this) und gibt das Objekt zurück
    val paul = Person("Paul").apply {
        age = 32
        city = "Angers"
    }
    println("apply: $paul")

    // 2 - also: eine zusätzliche Verarbeitung des Objekts (it), das zurückgegeben wird
    val persons = mutableListOf<Person>()
    val melanie = Person("Mélanie", 25).also { persons.add(it) }
    println("also: $melanie, persons=$persons")

    val length = paul.name.let { it.length * 2 }
    println("let: length=$length")
    for (city in listOf("Tours", null)) {
        val message = city?.let { "lives in ${it.uppercase()}" } ?: "unknown city"
        println("let and ?.: $message")
    }

    // 4 - run: eine Berechnung auf dem Objekt (this), die ein Ergebnis liefert
    val description = paul.run { "$name, $age years old, lives in $city" }
    println("run: $description")

    val summary = with(StringBuilder()) {
        append("Persons: ")

        toString()

    for (age in listOf(15, 40)) {
        val adult = Person("Jo", age).takeIf { it.age >= 18 }
        println("takeIf: ${adult ?: "minor"}")
    }
}

Es bleiben zwei Fragen. Die erste betrifft speziell Kotlin: Ist für einen funktionalen Parameter ein Funktionstyp erforderlich, oder genügt ein [fun interface]?

    • Der Funktionstyp ist die Standardwahl. Er erfordert keine Deklaration, wird wie eine Funktion aufgerufen, akzeptiert Lambdas und Referenzen direkt und profitiert von [inline]-Funktionen. Ein [typealias] gibt ihm einen Namen, wenn er lang ist;
    • das „fun“-Interface ist gerechtfertigt, wenn man einen wirklich eigenständigen Typ möchte (einen, der sich nicht mit einer anderen Funktion derselben Form verwechseln lässt), eine Methode mit aussagekräftigem Namen, zusätzliche Methoden mit Rumpf oder eine API, die auch für Java-Aufrufer gedacht ist: Für Java ist ein [fun interface] ein gewöhnliches funktionales Interface, verwendbar mit seinen Lambdas, während ein Kotlin-Funktionstyp dort als [Function2<Integer, Integer, Integer>] erscheint, dessen Methode [invoke] ein Objekt zurückgeben muss ([Unit] bei einer Funktion „ohne Rückgabewert“).

    Die zweite Frage ist dieselbe wie in Java: Soll das Interface eine einzige Methode oder mehrere haben?

    • Eine Funktion, ein Funktionstyp oder ein Interface mit einer einzigen Methode ist flexibler in der Verwendung: Jede vorhandene Funktion mit der richtigen Form passt, und mit einem Lambda kann man die Funktion sogar direkt an der Aufrufstelle schreiben. Es muss keine Klasse geschrieben werden. Diese Flexibilität erklärt, warum moderne Bibliotheken (Collections, die Coroutinen aus Kapitel 9, Spring) ausgiebig funktionale Parameter verwenden;
    • ein Interface mit mehreren Mitgliedern ist wieder im Vorteil, sobald das zu implementierende Verhalten mehrere zusammenhängende Operationen umfasst ([calculate] und [name] oben) oder wenn es einen eigenen Zustand und eine eigene Identität benötigt.

    Dies gilt für das Interface [ITaxDao] in der [dao]-Schicht aus Kapitel 6: Obwohl es nur ein Mitglied hat – die Eigenschaft [val taxBrackets: List<TaxBracket>] –, haben seine Implementierungen einen Zustand (die gelesenen Steuerstufen, den Dateinamen), werden vom Dependency-Injection-Container erzeugt und stellen eine klar benannte Rolle innerhalb der Anwendung dar. Ein [() -> List<TaxBracket>] hätte technisch genügt, wäre aber deutlich weniger aussagekräftig gewesen. Deshalb reservieren wir Funktionstypen für kurze, einmalige Verhalten (ein Kriterium, eine Transformation, eine Aktion) und „fachliche“ Interfaces für die Rollen der Anwendung, unabhängig von der Anzahl ihrer Mitglieder.

    7.6. Ereignisbehandlung

    7.6.1. Das Observer-Muster

    Als Parameter übergebene Funktionen dienen dazu, Ereignisse einzurichten. Wie Java hat Kotlin kein eigenes Schlüsselwort für Ereignisse (C# hat dafür das Schlüsselwort [event]): Es verwendet die Konventionen, die Java bereits seit Version 1.1 für grafische Komponenten und JavaBeans festgelegt hat, das sogenannte „Listener-Modell“. Eine Klasse [C1], die ein Ereignis [Xxx] signalisieren möchte, geht wie folgt vor:

    • Eine Klasse [XxxEvent] kapselt Informationen über das Ereignis, darunter das Objekt, das das Ereignis ausgelöst hat, die sogenannte Quelle. In Java ist es üblich, dass sie von [java.util.EventObject] abgeleitet wird, die die Quelle speichert; in Kotlin genügt eine gewöhnliche Klasse mit schreibgeschützten Eigenschaften, und genau das tun wir;
    • Ein Listener-Typ definiert die Form der Funktion, die beim Eintreten des Ereignisses aufgerufen wird. In Java ist das ein Interface namens [XxxListener]; in Kotlin ist es meist ein einfacher Funktionstyp, [(XxxEvent) -> Unit], der durch ein [typealias] benannt wird: Ein Listener ist ein Lambda oder eine Funktionsreferenz;
    • die Klasse [C1] verwaltet eine Liste von Funktionen und stellt zwei öffentliche Methoden zum An- und Abmelden bereit: [addXxxListener(listener)] und [removeXxxListener(listener)];
    • Möchte eine Instanz [c1] von [C1] das Ereignis signalisieren, erzeugt sie ein Objekt [XxxEvent] und ruft jeden der registrierten Listener auf, wobei sie ihnen dieses Objekt übergibt. Per Konvention übernimmt diese Benachrichtigung eine geschützte Methode [fireXxx(e: XxxEvent)] („fire“), die eine abgeleitete Klasse überschreiben kann, um die Veröffentlichung des Ereignisses zu ändern;
    • Möchte ein Objekt [c2] über das Ereignis [Xxx] des Objekts [c1] benachrichtigt werden, abonniert es sich mit [c1.addXxxListener(...)]. Es kann sich über [c1.removeXxxListener(...)] abmelden, wenn es nicht mehr benachrichtigt werden möchte. Da [c1] eine Liste verwaltet, können sich verschiedene Objekte für dasselbe Ereignis eintragen.

    In diesem Szenario haben wir:

    • eine Klasse, die ein Ereignis signalisiert (auch „veröffentlicht“ oder „sendet“ genannt);
    • Objekte, die über dieses Ereignis benachrichtigt werden. Man sagt, sie abonnieren das Ereignis oder tragen sich dafür ein: Das sind die Listener oder Ereignisbehandler;
    • einen Listener-Typ, der die Form der Funktionen definiert, die über das Ereignis benachrichtigt werden.

    Das ist das Entwurfsmuster Observer: Der Sender kennt seine Abonnenten nicht, er benachrichtigt sie lediglich. Dieses Modell bietet denselben Schutz wie ein eigenes Schlüsselwort: Die Liste der Listener ist eine private Eigenschaft des Senders. Von außen kann man sich nur an- oder abmelden; man kann weder die Liste leeren noch andere Listener ersetzen noch das Ereignis anstelle des Senders auslösen.

    private val listeners = CopyOnWriteArrayList<TemperatureTooHighListener>()

            field = value
            if (value > THRESHOLD) {
                // das Ereignis wird den Listenern signalisiert
                fireTemperatureTooHigh(TemperatureTooHighEvent(this, value))

        }

    // Registrierung eines Listeners
    fun addTemperatureTooHighListener(listener: TemperatureTooHighListener) {
        listeners.add(listener)

    // Abmeldung eines Listeners
    fun removeTemperatureTooHighListener(listener: TemperatureTooHighListener) {
        listeners.remove(listener)

    protected open fun fireTemperatureTooHigh(e: TemperatureTooHighEvent) {

            listener(e)

    }

    7.6.3. Ereignisse bei Eigenschaftsänderungen

    Der häufigste Ereignistyp tritt auf, wenn sich der Wert einer Eigenschaft eines Objekts ändert: Ein anderes Objekt (eine grafische Benutzeroberfläche, ein Cache, ein Protokoll) möchte über diese Änderung benachrichtigt werden. Kotlin und die Java-Bibliothek bieten dafür zwei einander ergänzende Werkzeuge:

    • Kotlins delegierte Eigenschaften. Eine als [var p: T by delegate] deklarierte Eigenschaft überträgt das Lesen und Schreiben ihres Werts an ein anderes Objekt, den Delegaten. Die Standardbibliothek stellt mehrere davon bereit, etwa [by lazy { … }], das den Wert der Eigenschaft beim ersten Zugriff berechnet. Der Parameter [property] ist eine Referenz auf die Eigenschaft ([KProperty]), deren Name über [property.name] ermittelt wird;
    • die Java-Klasse [java.beans.PropertyChangeSupport], die für uns die Liste der Listener verwaltet. class Thermometer(name: String) {
    // die Verwaltung der Listener wird an ein PropertyChangeSupport-Objekt delegiert
    private val changes = PropertyChangeSupport(this)

    // eine beobachtbare Eigenschaft: nach jedem Schreiben wird die Änderung signalisiert
    private fun <T> observable(initialValue: T): ReadWriteProperty<Any?, T> =
        Delegates.observable(initialValue) { property, old, new ->
            changes.firePropertyChange(property.name, old, new)
        }

    var name: String by observable(name)
    var temperature: Double by observable(0.0)

    // eine Eigenschaft, die Werte außerhalb des Intervalls [5, 30] ablehnt
    var setpoint: Double by Delegates.vetoable(20.0) { _, _, new -> new in 5.0..30.0 }

    // Registrierung und Abmeldung der Listener
    fun addPropertyChangeListener(listener: PropertyChangeListener) {
        changes.addPropertyChangeListener(listener)
    }

    fun addPropertyChangeListener(property: String, listener: PropertyChangeListener) {
        changes.addPropertyChangeListener(property, listener)
    }

    fun removePropertyChangeListener(listener: PropertyChangeListener) {
        changes.removePropertyChangeListener(listener)
    }

    val nbListeners: Int
        get() = changes.propertyChangeListeners.size

// Lambdas, Collections und Sequenzen

fun main() {
    val numbers = listOf(3, 8, 1, 6, 5, 4, 9, 2)

    // 1 - filter und map erwarten Funktionen (T) -> Boolean und (T) -> R
    val isEven: (Int) -> Boolean = { it % 2 == 0 }
    val square: (Int) -> Int = { it * it }
    println("collections: ${numbers.filter(isEven).map(square)}")
    // die Java Stream API bleibt verwendbar: die Lambdas werden in Predicate und Function konvertiert
    println("Stream: ${numbers.stream().filter { it % 2 == 0 }.map { it * it }.toList()}")

    // 2 - unsere eigene Filterfunktion, aufgerufen mit einem Lambda und dann mit einer Referenz
    println("filterBy(n > 4): ${numbers.filterBy { it > 4 }}")
    println("filterBy(isOdd): ${numbers.filterBy(::isOdd)}")

    // 3 - eine Collection wird sofort ausgewertet: jeder Schritt erzeugt eine vollständige Liste
    val largeList = numbers.filter {
        print("[test $it] ")
        it > 7
    }
    println()
    println("the list is already computed: $largeList")

    // 4 - eine Sequenz wird bei Bedarf ausgewertet:
    //     das Prädikat wird nur von der terminalen Operation aufgerufen
    val large = numbers.asSequence().filter {
        print("[test $it] ")
        it > 7
    }
    println("the sequence is defined, nothing has been executed yet")
    large.forEach { print("-> $it ") }
    println()

    // 5 - unsere eigenen Zwischenoperationen auf Sequenzen, ebenfalls lazy
    val cities = listOf("Angers", "Paris", "Lyon", "Nantes", "Aix")
    val result = cities.asSequence()
        .keep { it.length <= 5 }
        .transform(String::uppercase)
        .toList()
    println("our operations: $result")
    // eine unendliche Sequenz: nur die angeforderten Elemente werden berechnet
    val powersOfTwo = generateSequence(1) { it * 2 }
    val firstOnes = powersOfTwo.transform { "2^${it.countTrailingZeroBits()}=$it" }.take(5)
    println("powers of 2: ${firstOnes.toList()}")
}

// filtert eine Liste mit einem Prädikat: die Arbeit, die filter leistet
inline fun <T> List<T>.filterBy(predicate: (T) -> Boolean): List<T> {
    val result = mutableListOf<T>()
    for (element in this) {
        if (predicate(element)) {
            result.add(element)
        }
    }
    return result
}

fun isOdd(n: Int) = n % 2 != 0

// eine Zwischenoperation auf Sequenzen, die nur die Elemente durchlässt, die das Prädikat erfüllen
fun <T> Sequence<T>.keep(predicate: (T) -> Boolean): Sequence<T> = sequence {
    for (element in this@keep) {
        if (predicate(element)) yield(element)
    }
}

// eine Zwischenoperation, die jedes Element transformiert: das Äquivalent von map
fun <T, R> Sequence<T>.transform(transformation: (T) -> R): Sequence<R> = sequence {
    for (element in this@transform) {
        yield(transformation(element))
    }
}

    7.8. Ausdrucksbäume

    Einige Sprachen wie C# erlauben es, ein Lambda nicht in ausführbaren Code, sondern in eine Datenstruktur umzuwandeln, die es beschreibt (ein „Ausdrucksbaum“): Ein Programm kann dann das Lambda [t => t.Limit > 20000] analysieren und es beispielsweise in eine SQL-Klausel [WHERE limits > 20000] übersetzen, die vom Datenbankserver ausgeführt wird.

    Kotlin hat wie Java kein Äquivalent: Ein Kotlin-Lambda wird immer zu ausführbarem Code kompiliert; man kann es aufrufen, aber seine innere Funktionsweise nicht untersuchen. Mehrere Werkzeuge kommen dem jedoch nahe:

    • Eigenschaftsreferenzen: [Person::age] ist ein Objekt ([KProperty1<Person, Int>]), das den Namen der Eigenschaft ([Person::age.name]) und ihren Typ kennt. Eine Bibliothek kann dies nutzen, um eine Abfrage ohne Zeichenkette zu konstruieren: Das tut zum Beispiel Spring Data MongoDB mit seinen Kotlin-Erweiterungen, die es erlauben, ein Kriterium wie [Person::age gt 18] zu schreiben;
    • Interne DSL („Domain-Specific Languages“): Dank Lambdas mit Receivern, [infix]-Funktionen und Operatorüberladung kann eine Kotlin-Bibliothek eine SQL-ähnliche Syntax anbieten, die das Programm ausführt, um eine Datenstruktur zu konstruieren, die die Abfrage beschreibt. Das ist das Prinzip der Bibliothek Exposed von JetBrains: [Brackets.selectAll().where { Brackets.limit greater 20000 }];
    • Compiler-Plugins: Der Kotlin-Compiler lässt sich mit Plugins erweitern, die den Code transformieren. So funktioniert kotlinx.serialization, ebenso die Plugins [all-open] und [no-arg] , die mit Spring und Hibernate verwendet werden, oder das Plugin [power-assert], das den Ausdruck einer Assertion analysiert, um im Fehlerfall dessen Details anzuzeigen. Das sind jedoch Entwicklungswerkzeuge, keine integrierten Funktionen des Programms.

    Hibernate, das wir in Kapitel 11 behandeln werden, bietet dieselben Lösungen wie in Java: eine SQL-ähnliche Abfragesprache, die jedoch in Klassen und Eigenschaften ausgedrückt wird, HQL (["from Bracket t where t.limit > 20000"]), und die Criteria-API von Jakarta Persistence, die die Abfrage über Methodenaufrufe konstruiert ([cb.gt(t.get("limit"), 20000)]). In beiden Fällen besteht die Abfrage aus Daten (einer Zeichenkette oder einem Objektbaum), die Hibernate in SQL übersetzt, während ein an [filter] übergebenes Lambda innerhalb des Kotlin-Programms ausgeführt wird.

    7.9. Fazit

    Die wichtigsten Punkte dieses Kapitels:

    • In Kotlin sind Funktionen Werte: Sie haben einen Funktionstyp ([(Int, Int) -> Int], [() -> Unit], [(T) -> Boolean], [(() -> Unit)?], [T.() -> R]…), können in Variablen gespeichert, als Parameter übergeben, als Ergebnisse zurückgegeben und wie gewöhnliche Funktionen aufgerufen werden. Für die virtuelle Maschine sind sie Objekte, die die Interfaces [Function0], [Function1]… implementieren;
    • die Interfaces aus [java.util.function] ([Function], [Supplier], [Consumer], [Predicate]…) sowie [Runnable], [Callable] und [Comparator] bleiben verwendbar: Erwartet eine Java-Methode ein funktionales Interface, konvertiert Kotlin ein Lambda oder eine Referenz automatisch dorthin (SAM-Konvertierung); an anderer Stelle wird die Konvertierung explizit geschrieben: [Comparator { … }];
    • um einen Funktionstyp zu benennen, gibt es den Alias [typealias] (einfach ein Alias) und [fun interface] (ein echter neuer Typ, per Lambda implementierbar);
    • eine Funktion lässt sich über einen Lambda-Ausdruck gewinnen ([{ a, b -> a + b }], [{ it * it }] – außerhalb der Klammern geschrieben, wenn er der letzte Parameter ist, und mit [return@label] abgeschlossen), über eine anonyme Funktion, über ein anonymes Objekt oder über eine Referenz ([::function], [object::method], [Class::method], [::Class]). Zwei Referenzen auf dieselbe Funktion desselben Objekts sind gleich; zwei Lambdas sind niemals gleich;
    • Lambdas erfassen die sie umgebenden Variablen, auch die [var], die sie ändern können (der Compiler speichert sie in [Ref]-Objekten); sie sehen dann den Wert der Variablen zum Zeitpunkt ihrer Ausführung, was in Schleifen und zwischen Threads Vorsicht erfordert;
    • Funktionen, die Funktionen zurückgeben, und Erweiterungen von Funktionstypen ([then], [and], [or]…) setzen neue Funktionen zusammen; [compareBy], [thenBy] und [reversed] erzeugen Komparatoren;
    • die Funktionen [inline] kopieren ihren Code und den der Lambdas an die Aufrufstelle, ohne Objekt und Konvertierung, und erlauben nicht lokale Returns; [noinline] und [crossinline] behandeln Sonderfälle. Die Scope-Funktionen [let], [run], [with], [apply] und [also] sind die häufigsten Anwendungen davon;
    • einen Funktionstyp wählt man für kurzlebiges, einmaliges Verhalten; ein [fun interface] für einen eigenständigen Typ oder eine API, die von Java aus genutzt werden kann; ein Interface mit mehreren Mitgliedern (oder ein „fachliches“ Interface) für eine Rolle in der Anwendung;
    • ein Ereignis wird mit dem Listener-Muster eingerichtet: eine Klasse [XxxEvent], ein Listener-Typ (oft ein funktionaler [typealias]), [addXxxListener] / [removeXxxListener], und eine Liste von Funktionen ([CopyOnWriteArrayList]), die von einer Methode [fireXxx] durchlaufen wird. Die delegierten Eigenschaften [Delegates.observable] und [Delegates.vetoable] melden oder filtern Änderungen einer Eigenschaft, und [PropertyChangeSupport] verwaltet für sie die Liste der Listener;
    • Operationen auf Collections (unmittelbar, [inline]) und Sequenzoperationen (lazy) sind Funktionen höherer Ordnung; Kotlin hat keine Ausdrucksbäume, und Hibernate formuliert seine Abfragen mit HQL oder der Criteria-API.

    Lambdas tauchen in allen folgenden Kapiteln wieder auf: Ein Thread führt ein Lambda aus ([thread { … }]), und ein [ExecutorService] führt ein [Callable] aus (Kapitel 8); eine Coroutine wird mit [launch { … }] oder [async { … }] gestartet (Kapitel 9), Erweiterungsfunktionen von [ResultSet] erhalten in Form eines Lambdas die Transformation einer Ergebniszeile in ein Objekt (Kapitel 10), und Spring-Boot-Webservices verarbeiten HTTP-Anfragen in Methoden, die das Framework als Listener aufruft (Kapitel 13).
