    10. Datenbankzugriff mit JDBC

    10.1. Der JDBC-Treiber

    Greifen wir die Schichtenarchitektur wieder auf, die seit Kapitel 6 wiederholt verwendet wurde. Bisher hat die [dao]-Schicht der [Tax]-Anwendung drei Arten von Datenquellen genutzt:

    • im Code fest verdrahtete Daten ([HardwiredTax]);
    • Daten aus einer Textdatei ([FileTax]);
    • Daten aus einer JSON-Datei ([JsonTax]).

    In diesem Kapitel untersuchen wir den Fall, dass die Daten aus einer Datenbank stammen. Die Architektur sieht dann wie folgt aus:

    Im obigen Diagramm kommuniziert die [dao]-Schicht über eine für das verwendete DBMS spezifische Klassenbibliothek [2] mit dem [1] (Datenbankmanagementsystem) [3], das die Datenbank [4] verwaltet. Diese Bibliothek implementiert eine standardisierte API-Funktion der Java-Plattform, JDBC („Java DataBase Connectivity“), die seit Version 1.1 im Jahr 1997 Bestandteil des JDK ist. Man bezeichnet sie als JDBC-Treiber („JDBC driver“). Alle gängigen DBMS enthalten einen JDBC-Treiber, der als [.jar]-Archiv ausgeliefert wird.

    Kotlin besitzt keine eigene API für den Datenbankzugriff: Ein Kotlin-Programm, das auf der JVM läuft, verwendet JDBC direkt, so wie es NIO-Dateien oder Threads des JDK verwendet. Das ist einer der großen Vorteile der Sprache: Alle für Java geschriebenen JDBC-Treiber – und alle darauf aufbauenden Bibliotheken – lassen sich unverändert nutzen. Wie wir im Verlauf dieses Kapitels sehen werden, bietet Kotlin eine prägnantere und sicherere Art, JDBC-Code zu schreiben: eine Funktion [use] zum Schließen von Ressourcen, Erweiterungsfunktionen zum Lesen von Ergebnissen, Datenklassen zur Darstellung von Zeilen und keine geprüften Ausnahmen.

    JDBC ist in erster Linie eine Menge von Schnittstellen, die in den Paketen [java.sql] und [javax.sql] des Moduls [java.sql] im JDK definiert sind: [Connection], [Statement], [PreparedStatement], [ResultSet], [DataSource] … Ein JDBC-Treiber stellt Klassen bereit, die diese Schnittstellen implementieren. Der Anwendungscode hingegen interagiert nur mit den Schnittstellen: Er enthält in der Regel nicht die Namen der Klassen des Treibers. Das unterscheidet sich von anderen Plattformen, auf denen der Code oft direkt die für das jeweilige DBMS spezifischen Klassen verwendet ([MySqlConnection], [SqlConnection] … in C#): Auf der JVM ist die Abstraktion von Anfang an die Norm, und der Wechsel zu einem anderen DBMS bedeutet im Wesentlichen, den Treiber und die Adresse der Datenbank zu ändern, wie wir sehen werden. Dennoch hat jedes DBMS seinen eigenen SQL-Dialekt: Diese Unabhängigkeit hat ihre Grenzen, die wir ebenfalls untersuchen werden.

    Wir verwenden ein einziges DBMS, MySQL 8, das der Anhang „Das DBMS MySQL mit Laragon“ unter Windows installiert, zusammen mit seinem offiziellen JDBC-Treiber, MySQL Connector/J, Version 9.7.0. Die Datenbanken werden durch SQL-Skripte erstellt, die mit dem Kommandozeilenclient [mysql] ausgeführt werden; der Anhang zeigt auch, wie man sie mit dem grafischen Client HeidiSQL erstellt, der in Laragon enthalten ist.

    10.2. Die zwei Arten, eine Datenquelle zu nutzen

    Auf eine Datenbank kann auf zwei verschiedene Arten zugegriffen werden:

    • im verbundenen Modus;
    • im getrennten Modus.

    Im verbundenen Modus tut die Anwendung Folgendes:

    • Sie öffnet eine Verbindung zur Datenquelle;
    • sie arbeitet mit der Datenquelle im Lese-/Schreibmodus;
    • sie schließt die Verbindung.

    Im getrennten Modus tut die Anwendung Folgendes:

    • Sie öffnet eine Verbindung zur Datenquelle;
    • sie ruft eine Kopie aller oder eines Teils der Daten der Quelle in den Speicher ab;
    • sie schließt die Verbindung;
    • sie arbeitet mit der Kopie der Daten im Speicher, liest sie und schreibt in sie;
    • nach Abschluss der Arbeit öffnet sie eine Verbindung, sendet die geänderten Daten an die Datenquelle, damit diese aktualisiert wird, und schließt die Verbindung.

    Der verbundene Modus ist der Modus der Schnittstelle [ResultSet] von JDBC: Die Zeilen des Ergebnisses einer Abfrage werden gelesen, während die Verbindung geöffnet ist. Der getrennte Modus ist der der Schnittstelle [CachedRowSet] im Paket [javax.sql.rowset] (Java 5): eine Tabelle im Speicher, die aus einer Abfrage befüllt, offline geändert und anschließend mit ihren Änderungen an die Datenbank zurückgeschickt wird. Diese „RowSet“-Komponenten sind in JDK 25 noch vorhanden, werden in neuen Anwendungen aber kaum verwendet: Die Arbeit mit einer Kopie der Daten im Speicher und das spätere Speichern der Änderungen übernimmt heute ein ORM („Object-Relational Mapper“), der gewöhnliche Objekte statt Tabellenzeilen verarbeitet. Der am weitesten verbreitete ORM auf der JVM, Hibernate, ist Thema von Kapitel 11; er kann sowohl in Kotlin als auch in Java verwendet werden. Wir konzentrieren uns daher in erster Linie auf den verbundenen Modus – auf dem Hibernate aufbaut – und zeigen den getrennten Modus nur anhand eines Beispiels am Ende des Kapitels.

    10.3.2. Die vier grundlegenden Befehle der Sprache SQL

    SQL („Structured Query Language“) ist eine teilweise standardisierte Sprache zum Abfragen und Aktualisieren von Datenbanken. Alle DBMS-Dialekte halten den standardisierten Teil von SQL ein, fügen der Sprache aber proprietäre Erweiterungen hinzu, die ihre spezifischen Eigenschaften nutzen. Zwei Beispiele dafür sind uns bereits begegnet: Die automatische Erzeugung von Primärschlüsseln und die zulässigen Datentypen für Tabellenspalten hängen oft vom DBMS ab.

    Die vier grundlegenden SQL-Befehle, die wir hier vorstellen, sind standardisiert und werden von allen DBMS akzeptiert:

    Befehl
    Rolle
    [select col1, col2, … from table1, table2, … where condition order by expression]
    Die Abfrage zum Abrufen von Daten aus einer Datenbank. Nur die Schlüsselwörter [select] und [from] sind obligatorisch. Mit allen Tabellen, die auf das Schlüsselwort [from] folgen, wird ein Join durchgeführt; nur die Spalten, die auf das Schlüsselwort [select] folgen, bleiben erhalten; nur die Zeilen, die die Bedingung des Schlüsselworts [where] erfüllen, bleiben erhalten; die resultierenden Zeilen, sortiert nach dem Ausdruck im Schlüsselwort [order by], bilden das Ergebnis der Abfrage. Dieses Ergebnis ist eine Tabelle.
    [insert into table(col1, col2, …) values (val1, val2, …)]
    Fügt eine Zeile in [table] ein. [(col1, col2, …)] gibt die Spalten der Zeile an, die mit den Werten [(val1, val2, …)] initialisiert werden sollen.
    [update table set col1=val1, col2=val2, … where condition]
    Aktualisiert die Zeilen in [table] anhand von [condition] (alle Zeilen, wenn es kein [where] gibt). Für diese Zeilen wird die Spalte [coli] auf [vali] gesetzt.
    [delete from table where condition]
    Löscht alle Zeilen aus [table] , die [condition] erfüllen (alle Zeilen, wenn es kein [where] gibt).

    10.3.3. Die grundlegenden JDBC-Schnittstellen für den verbundenen Modus

    Kehren wir zum Diagramm einer Anwendung zurück, die über einen JDBC-Treiber auf eine Datenbank zugreift:

    Im verbundenen Modus tut die Anwendung Folgendes:

    • Sie öffnet eine Verbindung zur Datenquelle;
    • sie arbeitet mit der Datenquelle im Lese-/Schreibmodus;
    • sie schließt die Verbindung.

    An diesen Operationen sind im Wesentlichen drei Arten von Objekten beteiligt:

    • die Verbindung ([Connection]), die die Eigenschaften und Methoden der Datenbankverbindung kapselt;
    • der SQL-Befehl ([Statement] oder [PreparedStatement] für einen parametrisierten Befehl), der die Eigenschaften und Methoden des ausgeführten SQL-Befehls kapselt;
    • das Ergebnis ([ResultSet]), das die Eigenschaften und Methoden des Ergebnisses eines SQL- oder [select]-Befehls kapselt.

    Dies sind Schnittstellen aus dem Paket [java.sql]. Der MySQL-Treiber implementiert sie mit Klassen aus seinen eigenen Paketen ([com.mysql.cj.jdbc.ConnectionImpl], [ClientPreparedStatement], [ResultSetImpl] …), die die Anwendung nicht kennen muss: Sie erhält ihre Objekte über Methoden, die Schnittstellen zurückgeben. Die Verbindung wird von der Klasse [DriverManager] (oder von einer Datenquelle [DataSource], auf die wir später eingehen) geliefert, der SQL-Befehl wird von der Verbindung erzeugt, und das Ergebnis wird vom SQL-Befehl zurückgegeben.

    Dies sind Java-Schnittstellen. Kotlin verwendet sie nach seinen üblichen Regeln für den Zugriff auf Java-Code: Ein Paar von Accessoren [getXxx] / [setXxx] wird als Eigenschaft [xxx] verwendet ([result.metaData] statt [result.getMetaData()], [connection.autoCommit = false] statt [connection.setAutoCommit(false)]), und die von einer Java-Methode zurückgegebenen Werte haben einen Plattformtyp (in Compilermeldungen als [String!] bezeichnet): Kotlin weiß nicht, ob sie [null] sein können, und überlässt es dem Entwickler, zu entscheiden, ob er sie als [String] oder als [String?] behandelt (Kapitel 3). Das ist wichtig für Spalten, die die SQL-Werte [NULL] enthalten können.

    10.3.3.1. Die Schnittstelle Connection

    Diese Schnittstelle dient der Verwaltung der Verbindung zur Datenbank. Eine Verbindung erhält man über die statische Methode [DriverManager.getConnection(url, user, password)], die als Parameter die URL der Datenbank im Format JDBC – zum Beispiel [jdbc:mysql://localhost:3306/dbarticles] – sowie die Anmeldedaten des Benutzers erwartet. Die zurückgegebene Verbindung ist bereits geöffnet. Die Methoden der Schnittstelle [Connection], die wir verwenden werden, sind die folgenden:

    Methode
    Rolle
    [createStatement]
    Erzeugt einen SQL-Befehl, der dieser Verbindung zugeordnet ist.
    [prepareStatement]

    10.3.3.3. Die Schnittstelle ResultSet

    Diese Schnittstelle kapselt die Ergebnisse eines SQL-[select]-Befehls.     10.3.4. Fehlerbehandlung

    Die [dao]-Schicht kann beim Betrieb der Datenbank auf zahlreiche Fehler stoßen: Server nicht erreichbar, Datenbank nicht vorhanden, falsches Passwort, SQL-Syntaxfehler, Verletzung einer Integritätsbedingung usw. Diese werden als [SQLException]-Ausnahmen gemeldet. In Java ist [SQLException] eine geprüfte Ausnahme (Checked Exception): Alle Methoden von JDBC deklarieren sie in ihrer [throws]-Klausel, und der Java-Compiler verlangt, dass der aufrufende Code sie entweder abfängt oder seinerseits deklariert. Kotlin kennt keine geprüften Ausnahmen (Kapitel 3): Der Compiler stellt keine Anforderungen, und eine Kotlin-Funktion, die JDBC aufruft, muss nichts deklarieren. Das ist zugleich Freiheit und Verantwortung: Nichts weist den Entwickler darauf hin, dass eine Zeile fehlschlagen kann; er muss selbst entscheiden, wo Fehler behandelt werden. Eine [dao]-Schicht muss diese Fehler behandeln und, was auch geschieht, die erworbenen Ressourcen freigeben: Die Verbindung, der SQL-Befehl und das Ergebnis müssen geschlossen werden.     • Zeilen 3–5: Drei Ressourcen werden geöffnet, jeweils mit einem *[use]. Das geöffnete Objekt ist der Lambda-Parameter ([connection], [statement], [result]); wir geben ihm einen Namen, statt [it] zu verwenden, denn die drei Lambdas sind verschachtelt, und ein [it] würde sich auf das Objekt des innersten [use] beziehen. Anders als try-with-resources in Java, das mehrere Ressourcen in seinen Klammern akzeptiert, behandelt *[use] nur eine Ressource: Deshalb verschachteln wir die [use]s. Die Ressourcen werden in umgekehrter Reihenfolge ihrer Öffnung geschlossen: zuerst das Ergebnis, dann der SQL-Befehl, dann die Verbindung. Eine Ausnahme, die beim Schließen geworfen wird, überdeckt nicht diejenige, die möglicherweise zum Verlassen des Blocks geführt hat: Sie wird ihr als „unterdrückte“ Ausnahme ([suppressedExceptions]) angehängt, wie in Java;
    • Zeile 13: Die Klausel [catch] fängt sowohl Verbindungs- und Ausführungsfehler als auch Fehler beim Schließen ab.

    Da [use] eine [inline]-Funktion ist (Kapitel 7), ist ihr Block kein Lambda-Objekt: Er wird anstelle des Aufrufs kopiert, und eine im Block geschriebene [return]-Anweisung beendet die umgebende Funktion, nachdem die Ressource geschlossen wurde. Außerdem gibt [use] den Wert seines Blocks zurück: [val n = connection.createStatement().use { it.executeUpdate(sql) }] führt den Befehl aus, schließt das [Statement]-Objekt und gibt die Anzahl der geänderten Zeilen zurück. Wir werden diese beiden Eigenschaften häufig nutzen.

    Der Nutzen von [use] liegt nicht nur in der Einsparung von Zeilen: Es erspart dem Entwickler, die Verbindung manuell zu schließen. Das Vergessen des Schließens einer Verbindung kann jedoch unbemerkt bleiben und die Anwendung scheinbar zufällig „abstürzen“ lassen, sobald das DBMS (oder der Connection-Pool, den wir später behandeln) die maximale Anzahl der offenen Verbindungen erreicht, die es unterstützt. Im weiteren Verlauf dieses Kurses wird jede JDBC-Ressource mit einer use-Anweisung geöffnet.

    Die Klasse [SQLException] liefert drei Informationen über den Fehler, die Kotlin als Eigenschaften darstellt:

    • [message]: die Fehlermeldung;
    • [errorCode]: der DBMS-spezifische Fehlercode (die MySQL-Fehlernummer: 1049, 1062 …);
    • [sqlState]: ein vom SQL-Standard definierter fünfstelliger Fehlercode („SQLSTATE“), der bei den häufigsten Fehlern allen DBMS gemeinsam ist: Die Klasse [42] bezeichnet einen Syntax- oder Zugriffsfehler, [23] eine Verletzung einer Integritätsbedingung, [08] einen Verbindungsfehler …

    Beachten Sie die Eigenschaft [sqlState], die von der Java-Methode [getSQLState] abgeleitet ist: Beginnt ein Name mit mehreren Großbuchstaben, wandelt Kotlin sie in Kleinbuchstaben um, mit Ausnahme des letzten, wenn er das nächste Wort einleitet ([SQLState] wird zu [sqlState]). Wir fügen der Kotlin-Funktion daher die Annotation [@Throws(SQLException::class)] hinzu, die die von Java erwartete [throws]-Klausel erzeugt. Unsere Programme, die vollständig in Kotlin geschrieben sind, benötigen dies nicht.

    Path.of(file).bufferedReader().use { config.load(it) }

    10.3.7. Ausführen einer SELECT-Anfrage

    Die Ausführung von SQL-Befehlen umfasst die folgenden Schritte:

    • Verbindung zur Datenbank herstellen;
    • die SQL-Befehle an die Datenbank senden;
    • die Ergebnisse der SQL-Befehle verarbeiten;
    • die Verbindung schließen.

    Die Schritte 2 und 3 können wiederholt werden; die Verbindung wird erst am Ende der Datenbankverarbeitung geschlossen. Offene Verbindungen sind in einem DBMS begrenzte Ressourcen: Man muss sparsam mit ihnen umgehen und versucht stets, die Lebensdauer einer offenen Verbindung zu begrenzen. In unserem Programm wird die Verbindung nach jedem SQL-Befehl geschlossen, und für den nächsten Befehl wird eine neue Verbindung geöffnet.

    Das Öffnen einer Verbindung ist jedoch aufwendig: Es erfordert den Aufbau einer Netzwerkverbindung zum Server, gegebenenfalls das Aushandeln einer Verschlüsselung und eine Authentifizierung. [DriverManager] tut nichts, um diese Kosten zu senken: Jeder Aufruf von [getConnection] öffnet eine neue Netzwerkverbindung, und jedes [close] schließt sie tatsächlich. Für ein interaktives Werkzeug wie dieses ist das kein Problem. Eine Anwendung, die viele SQL-Befehle ausführt – zum Beispiel ein Webserver –, verwendet stattdessen einen Verbindungspool: Wenn die Anwendung eine Verbindung schließt, schließt der Pool sie nicht wirklich, sondern nimmt sie wieder in den Pool auf; fordert die Anwendung eine neue Verbindung an, erhält sie eine der bereits aufgebauten Verbindungen aus dem Pool. Der Vorteil dieses Systems ist, dass es für den Entwickler transparent ist: Der Code, der Verbindungen mit [use] öffnet und schließt, muss nicht geändert werden. Wie man ihn verwendet, sehen wir im Abschnitt „Datenquellen und Verbindungspools“. Eine Verbindung zu Beginn jeder Operation zu öffnen und am Ende wieder zu schließen, ist daher bewährte Praxis.

private fun executeSelect(parameters: ConnectionParameters, query: String) {
    try {
        // die Verbindung, die SQL-Anweisung und das Ergebnis werden beim Verlassen ihres [use]-Blocks geschlossen
        parameters.connect().use { connection ->
            connection.createStatement().use { statement ->
                statement.executeQuery(query).use { result ->
                    // Anzeige der Ergebnisse
                    displayResultSet(result)
                }
            }
        }
    } catch (e: SQLException) {
        println("Database access error (${e.message})")
    }
}

// Anzeige der Zeilen eines select-Ergebnisses
private fun displayResultSet(result: ResultSet) {

    val metadata = result.metaData
    val columns = 1..metadata.columnCount
    val header = columns.joinToString(",") { metadata.getColumnLabel(it) }
    val dashes = "-".repeat(header.length)
    println("\n$dashes\n$header\n$dashes\n")
    // die Zeilen, eine nach der anderen
    while (result.next()) {
        println(columns.joinToString(" ") { "${result.getObject(it)}" })
    }

    10.4.2. Datenquellen und Verbindungspools

    [DriverManager] ist der traditionelle Weg, eine Verbindung zu erhalten. Seit JDBC 2.0 verwenden Anwendungen stattdessen bevorzugt eine Datenquelle – ein Objekt, das die Schnittstelle [javax.sql.DataSource] implementiert. Eine Datenquelle wird einmalig konfiguriert (URL, Benutzername, Passwort, Treibereinstellungen) und liefert dann Verbindungen über ihre Methode [getConnection()] ohne Parameter (die Eigenschaft [connection] in Kotlin). Der Code, der die Datenquelle verwendet, kennt weder die URL noch die Zugangsdaten: In einer Anwendung wird die Datenquelle selbst im Dependency-Injection-Container registriert (Kapitel 6) und nicht die Verbindungsparameter. Es gibt zwei Hauptkategorien von Datenquellen:

    • die von Treibern bereitgestellten, wie [com.mysql.cj.jdbc.MysqlDataSource] für MySQL. Wie [DriverManager] öffnen sie bei jedem Aufruf von [getConnection] eine neue Netzwerkverbindung;
    • die, die einen Verbindungspool verwalten. Am häufigsten verwendet wird HikariCP, der Standard-Verbindungspool von Spring Boot. [getConnection] gibt eine Verbindung aus dem Pool zurück, und [close] gibt diese Verbindung an den Pool zurück, anstatt sie zu schließen.

    Der zweite Teil des Programms, [Jdbc03], vergleicht die beiden (Zeilen 39–55 und die Funktion [measure]):

    • Zeilen 40–43: eine Datenquelle [MysqlDataSource]. [user = "root"] ruft die Java-Methode [setUser] auf, und [password = ""] ruft die Methode [setPassword] auf.     10.4.3. Welche Abstraktionsebene sollte man wählen?

    Die Unabhängigkeit von JDBC vom DBMS erscheint ideal. In der Praxis kann JDBC nicht alle Besonderheiten eines DBMS verbergen:

    • Das SQL selbst unterscheidet sich von einem DBMS zum anderen, sobald man über die Grundbefehle hinausgeht: Erzeugung von Primärschlüsseln, Begrenzung der Anzahl zurückgegebener Zeilen ([limit 10] bei MySQL und PostgreSQL, [top 10] oder [offset … fetch] bei SQL Server), Spaltentypen, Datumsfunktionen usw.;
    • die von [getObject] zurückgegebenen Typen können variieren: Wir werden sehen, dass [count(*)] bei MySQL einen [Long] zurückgibt;
    • Fehlercodes ([errorCode]) sind für jedes DBMS spezifisch, und SQLSTATE-Werte werden nicht immer auf dieselbe Weise verwendet;
    • die URL und die Konfigurationsparameter sind für jeden Treiber spezifisch.

    Die Anfrageparameter sind dagegen einheitlich: JDBC schreibt die Notation [?] vor (Positionsparameter, ohne Namen), die jeder Treiber in die Syntax seines DBMS übersetzt.

    Um diese Einschränkungen zu überwinden oder das Schreiben von JDBC-Code zu vereinfachen, verwendet man heute vor allem Folgendes:

    • einen ORM – meist Hibernate, wie in Kapitel 11 behandelt –, bei dem die [dao]-Schicht Objekte verwaltet und ihre Anfragen in HQL schreibt, einer objektorientierten Abfragesprache; Hibernate erzeugt das für jedes DBMS spezifische SQL (seinen „Dialekt“);
    • Bibliotheken, die das SQL beibehalten, aber den sich wiederholenden Code von JDBC beseitigen: Springs [JdbcTemplate] und [JdbcClient] (letzteres seit Spring Framework 6.1), die Zeilen von [select] direkt in Objekte umwandeln und [SQLException] in ungeprüfte Ausnahmen überführen; jOOQ, das SQL-Anfragen im Code mit Validierung durch den Compiler aufbaut und Erweiterungen für Kotlin bietet; MyBatis, das in XML-Dateien oder Annotationen geschriebene SQL-Anfragen mit Methoden verknüpft;
    • Auf der Kotlin-Seite bietet Exposed, die Datenbankzugriffsbibliothek von JetBrains, beide Stile: eine in Kotlin geschriebene Abfragesprache ([Articles.selectAll().where { Articles.price greater 200 }]) und eine schlanke Objektschicht.

    Diese Werkzeuge beruhen alle auf JDBC: JDBC zu verstehen bleibt nützlich, um nachzuvollziehen, was sie tun, und um Probleme mit ihnen zu beheben. Und wie wir sehen werden, genügen einige wenige Erweiterungsfunktionen, um den in Kotlin geschriebenen JDBC-Code deutlich weniger repetitiv zu machen.

// alle (verbleibenden) Zeilen des Ergebnisses, jede durch [transformation] transformiert
fun <T> ResultSet.toList(transformation: (ResultSet) -> T): List<T> {
    val list = mutableListOf<T>()
    while (next()) {
        list.add(transformation(this))
    }
    return list
}

// dieselben Zeilen, bei Bedarf gelesen: die Sequenz muss durchlaufen werden, bevor das Ergebnis geschlossen wird

    generateSequence { if (next()) transformation(this) else null }

fun main() {

        // die Artikel, deren Name auf 3 endet
        println("Articles whose name ends with 3:")
        getArticles("%3").forEach(::println)
    } catch (ex: SQLException) {

    }
}

// Einfügen einer Liste von Artikeln mit einer parametrisierten Query
private fun insertArticles(articles: List<Article>) {
    // die parametrisierte Query: jedes ? ist ein Parameter, ab 1 nummeriert
    val query = "insert into articles(name, price, currentstock, minimumstock) values(?, ?, ?, ?)"
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.prepareStatement(query, Statement.RETURN_GENERATED_KEYS).use { statement ->
            // Einfügen der Zeilen: nur der Wert der Parameter ändert sich
            for (article in articles) {
                statement.setString(1, article.name)
                statement.setBigDecimal(2, article.price)
                statement.setInt(3, article.currentStock)
                statement.setInt(4, article.minimumStock)
                statement.executeUpdate()
                // der vom DBMS erzeugte Primärschlüssel
                statement.generatedKeys.use { keys ->
                    keys.next()
                    println("article [${article.name}] inserted with id ${keys.getInt(1)}")
                }
            }
        }
    }
}

// die Artikel, deren Name zum Muster [like] passt
private fun getArticles(pattern: String): List<Article> {
    val query = """
        select id, name, price, currentstock, minimumstock from articles
        where name like ? order by id
    """.trimIndent()
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.prepareStatement(query).use { statement ->
            statement.setString(1, pattern)
            // jede Zeile des Ergebnisses wird zu einem Article-Objekt
            return statement.executeQuery().use { result -> result.toList { it.toArticle() } }
        }
    }
}

private fun executeUpdate(query: String): Int =
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.createStatement().use { statement -> statement.executeUpdate(query) }
    }

Das interaktive Programm [Jdbc01.kt] hält diese Regel schon seiner Natur nach nicht ein: Es führt die vom Benutzer eingegebenen SQL-Befehle aus. Es ist ein Administrationswerkzeug, kein Beispiel, dem man folgen sollte.

    10.6. Transaktionen

    10.6.1. Allgemeines

    Eine Transaktion ist eine Folge von SQL-Befehlen, die „atomar“ ausgeführt werden:

    • entweder gelingen alle Operationen;
    • oder eine von ihnen schlägt fehl, und dann werden alle vorangegangenen Operationen rückgängig gemacht.

    Am Ende werden entweder alle Operationen einer Transaktion erfolgreich angewendet, oder keine. Das klassische Beispiel ist eine Banküberweisung: Die Abbuchung von einem Konto und die Gutschrift auf einem anderen müssen entweder beide erfolgen oder keine von beiden. Wenn die Anwendung die Transaktion selbst steuert, bestätigt sie sie mit einem Befehl [COMMIT] oder macht sie mit einem Befehl [ROLLBACK] rückgängig.

    In unseren bisherigen Beispielen haben wir keine Transaktion verwendet. Und dennoch gab es Transaktionen, denn in einem DBMS wird ein SQL-Befehl immer innerhalb einer Transaktion ausgeführt. Wenn die Anwendung nicht selbst eine explizite Transaktion startet, verwendet das DBMS eine implizite Transaktion. Dann gibt es zwei Fälle:

    • Jeder SQL-Befehl ist Teil einer Transaktion, die das DBMS vor dem Befehl öffnet und danach bestätigt. Man spricht vom Autocommit-Modus. Es verhält sich so, als würde die Anwendung für jeden SQL-Befehl eine Transaktion starten;
    • das DBMS befindet sich nicht im Autocommit-Modus: Es startet mit dem ersten außerhalb einer Transaktion abgesetzten SQL-Befehl eine implizite Transaktion und überlässt es der Anwendung, sie abzuschließen. Alle folgenden SQL-Befehle sind Teil dieser impliziten Transaktion, die aufgrund verschiedener Ereignisse (Schließen der Verbindung, Beginn einer neuen Transaktion usw.) nach Regeln enden kann, die für das DBMS spezifisch sind. Dieser Modus sollte vermieden werden.

    JDBC erzwingt den ersten Fall: Eine JDBC-Verbindung befindet sich beim Öffnen im Autocommit-Modus, unabhängig von der Einstellung des DBMS (MySQL befindet sich mit der Standard-Storage-Engine InnoDB ebenfalls im Autocommit-Modus).

    Befehle verschiedener Benutzer werden gleichzeitig in parallel laufenden Transaktionen ausgeführt. Operationen einer Transaktion können Auswirkungen auf die einer anderen haben. Es gibt vier Isolationsstufen zwischen den Transaktionen verschiedener Benutzer:

    • Read Uncommitted;
    • Read Committed;
    • Repeatable Read;
    • Serializable.

    Read Uncommitted

    Diese Isolationsstufe ist auch als „Dirty Read“ bekannt. Hier ein Beispiel dafür, was in diesem Modus passieren kann:

    • Ein Benutzer namens U1 startet eine Transaktion auf der Tabelle T;
    • ein Benutzer namens U2 startet eine Transaktion auf derselben Tabelle T;
    • Benutzer U1 ändert Zeilen der Tabelle T, hat die Änderungen aber noch nicht bestätigt;
    • Der Benutzer U2 „sieht“ diese Änderungen und trifft Entscheidungen auf der Grundlage dessen, was er sieht;
    • Benutzer U1 bricht seine Transaktion mit einem [ROLLBACK] ab.

    In Schritt 4 hat Benutzer U2 eine Entscheidung auf der Grundlage von Daten getroffen, die sich später als falsch herausstellten.

    Read Committed

    Diese Isolationsstufe vermeidet die vorherige Falle: In Schritt 4 „sieht“ Benutzer U2 die Änderungen von Benutzer U1 an der Tabelle T nicht. Er sieht sie erst, nachdem U1 seine Transaktion mit einem [COMMIT] bestätigt hat. In diesem Modus kann jedoch die folgende Situation eintreten:

    • ein Benutzer U1 startet eine Transaktion auf der Tabelle T;
    • ein Benutzer U2 startet eine Transaktion auf derselben Tabelle T;
    • Benutzer U2 führt ein [select] aus, um den Durchschnitt der Spalte C für die Zeilen von T zu berechnen, die eine bestimmte Bedingung erfüllen;
    • Benutzer U1 ändert ([update]) bestimmte Werte der Spalte C von T und bestätigt die Änderungen ([commit]);
    • Benutzer U2 wiederholt dasselbe [select] wie in Schritt 3. Er stellt fest, dass sich der Durchschnitt der Spalte C aufgrund der von U1 vorgenommenen Änderungen verändert hat.

    Benutzer U2 sieht nun nur die von U1 bestätigten Änderungen, doch innerhalb derselben Transaktion liefern zwei identische Operationen unterschiedliche Ergebnisse. Diese Situation nennt man „Non-repeatable Read“. Sie ist problematisch für jeden, der eine konsistente Sicht auf die Tabelle T benötigt.

    Repeatable Read

    Bei dieser Isolationsstufe ist einem Benutzer garantiert, dass er bei Lesezugriffen auf die Datenbank dieselben Ergebnisse erhält, solange er innerhalb derselben Transaktion bleibt. Er arbeitet auf einem „Schnappschuss“ der Daten, der die Änderungen anderer Transaktionen nicht widerspiegelt, selbst wenn diese bestätigt wurden. Er sieht diese Änderungen erst, wenn er seine eigene Transaktion abgeschlossen hat.

    Diese Isolationsstufe ist theoretisch noch nicht perfekt: Eine andere Transaktion kann Zeilen hinzufügen ([insert]), die die Bedingung aus Schritt 3 erfüllen, was das Ergebnis eines späteren Lesezugriffs verändern würde. Diese Zeilen nennt man „Phantomzeilen“ („Phantom Reads“). Dies ist die Standard-Isolationsstufe von MySQL (InnoDB), die bei einfachen Lesezugriffen auch Phantom Reads verhindert.

    Serializable

    In diesem Isolationsmodus sind die Transaktionen vollständig voneinander isoliert: Das Ergebnis zweier gleichzeitig ausgeführter Transaktionen ist dasselbe, als wären sie nacheinander ausgeführt worden. Um dies zu erreichen, sperrt das DBMS die gelesenen Daten und lässt Transaktionen, die versuchen, sie zu ändern, warten (oder scheitern). Diese Stufe verringert die Parallelität und damit die Leistung.

    Die vier Isolationsstufen sind nicht in allen DBMS verfügbar. Die Standard-Isolationsstufe ist im Allgemeinen Read Committed (SQL Server, PostgreSQL, Oracle) oder Repeatable Read (MySQL). Die gewünschte Isolationsstufe kann von der Anwendung ausdrücklich angegeben werden.

    10.6.2. Transaktionsverwaltung in der API

    Bei JDBC werden Transaktionen von der Verbindung verwaltet. Es gibt kein „Transaktionsobjekt“: Eine Verbindung hat höchstens eine aktive Transaktion, und alle auf dieser Verbindung ausgeführten SQL-Befehle gehören zu ihr. Die relevanten Methoden der Schnittstelle [Connection] sind die folgenden. Kotlin behandelt die Java-Getter-Setter-Paare [getXxx] / [setXxx] als Eigenschaften (Kapitel 4): [connection.setAutoCommit(false)] wird als [connection.autoCommit = false] geschrieben, und [connection.getAutoCommit()] wird als [connection.autoCommit] geschrieben. Die linke Spalte zeigt die Kotlin-Form:

    Methode oder Eigenschaft
    Rolle
    [autoCommit]
    [autoCommit = false] ([setAutoCommit(false)] in Java) verlässt den Autocommit-Modus: Die folgenden SQL-Befehle gehören zu einer Transaktion, die mit dem ersten von ihnen beginnt und mit [commit] oder [rollback] endet. Mit dem nächsten Befehl beginnt dann eine neue Transaktion. [autoCommit = true] kehrt in den Autocommit-Modus zurück und bestätigt dabei die laufende Transaktion.
    [commit()]
    bestätigt die Transaktion: Die Ergebnisse der innerhalb der Transaktion abgesetzten SQL-Befehle werden endgültig und für andere Transaktionen sichtbar.
    [rollback()]
    macht die Transaktion rückgängig: Die Ergebnisse der in der Transaktion abgesetzten SQL-Befehle werden zurückgenommen.
    [setSavepoint()]
    setzt in der aktuellen Transaktion einen Sicherungspunkt (ein [Savepoint]-Objekt). Dies ist keine Zugriffsmethode (es gibt kein zugehöriges [getSavepoint]): Kotlin ruft sie als Funktion auf.
    [rollback(Savepoint)]
    macht die seit dem Sicherungspunkt ausgeführten SQL-Befehle rückgängig, ohne die davor liegenden zurückzunehmen: Die Transaktion wird fortgesetzt.
    [transactionIsolation]
    die Isolationsstufe der Transaktionen der Verbindung ([setTransactionIsolation] in Java). Sie muss gesetzt werden, bevor eine Transaktion beginnt.

    Die Isolationsstufe ist eine der Konstanten der Schnittstelle [Connection]:

    Wert
    Bedeutung
    [TRANSACTION_READ_UNCOMMITTED]
    Eine Transaktion kann Daten lesen, die von einer anderen Transaktion geschrieben, von dieser aber noch nicht bestätigt wurden. Dies sollte vermieden werden.
    [TRANSACTION_READ_COMMITTED]
    Die Transaktion kann keine Daten lesen, die von einer anderen Transaktion geschrieben, von dieser aber noch nicht bestätigt wurden. Daten, die innerhalb der Transaktion zweimal hintereinander gelesen werden, können sich jedoch ändern, weil eine andere Transaktion sie in der Zwischenzeit geändert haben kann; eine andere Transaktion kann auch Zeilen hinzugefügt haben (Geisterzeilen).
    [TRANSACTION_REPEATABLE_READ]
    Die von der Transaktion gelesenen Daten ändern sich nicht, bis die Transaktion abgeschlossen ist. Theoretisch verhindert dies nicht, dass eine andere Transaktion Zeilen hinzufügt.
    [TRANSACTION_SERIALIZABLE]
    Alles verhält sich so, als würde die Transaktion allein laufen. Das verringert die Leistung, weil die Transaktionen nicht mehr parallel laufen.

    Dies sind [static]-Konstanten einer Java-Schnittstelle: Kotlin verweist auf sie über den Namen der Schnittstelle, [Connection.TRANSACTION_READ_COMMITTED], genau wie auf die Mitglieder eines [companion object].

    Eine Verbindung, die den Autocommit-Modus verlassen hat, muss geschlossen werden, nachdem ihre Transaktion bestätigt oder rückgängig gemacht wurde. Wird sie geschlossen, während noch eine Transaktion läuft, hängt das Ergebnis vom Treiber ab (Connector/J macht sie rückgängig): Man muss eine Transaktion immer ausdrücklich bestätigen.

    package jdbc06

import common.Article
import common.transaction
import java.math.BigDecimal
import java.sql.Connection
import java.sql.DriverManager
import java.sql.PreparedStatement
import java.sql.SQLException

// Transaktionen

private const val URL = "jdbc:mysql://localhost:3306/dbarticles"
private const val USER = "root"
private const val PASSWORD = ""

fun main() {
    println("JDBC URL of the database: [$URL]")

    // zwei Artikel mit demselben Namen: die Eindeutigkeitsbedingung UNQ_NAME lehnt den zweiten ab
    val articles = listOf(
        Article(0, "article", BigDecimal("100"), 10, 1),
        Article(0, "article", BigDecimal("200"), 20, 2),
    )

    try {
        // 1 - Einfügen ohne explizite Transaktion
        println("\nInsertion without a transaction...")
        executeUpdate("delete from articles")
        try {
            insertArticlesOutOfTransaction(articles)
        } catch (ex: SQLException) {
            println("Database access error (${ex.message})")
        }
        displayArticles()

        // 2 - dasselbe in einer Transaktion
        println("\nInsertion in a transaction...")
        executeUpdate("delete from articles")
        insertArticlesInTransaction(articles)
        displayArticles()

        // 3 - eine Transaktion mit Savepoint
        println("\nInsertion in a transaction with a savepoint...")
        executeUpdate("delete from articles")
        insertArticlesWithSavepoint(articles)
        displayArticles()

        // 4 - eine Transaktion, verwaltet von der Higher-Order-Funktion [transaction]
        println("\nInsertion in a transaction managed by the [transaction] function...")
        executeUpdate("delete from articles")
        try {
            insertArticlesWithFunction(articles)
        } catch (ex: SQLException) {
            println("transaction rolled back (${ex.message})")
        }
        insertArticlesWithFunction(articles.take(1))
        displayArticles()
    } catch (ex: SQLException) {
        println("Database access error (${ex.message})")
    }
}

// Einfügen einer Liste von Artikeln ohne explizite Transaktion (Autocommit-Modus)
private fun insertArticlesOutOfTransaction(articles: List<Article>) {
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        createInsertStatement(connection).use { statement ->
            articles.forEach { insertArticle(statement, it) }
        }
    }
}

// Einfügen einer Liste von Artikeln in einer Transaktion
private fun insertArticlesInTransaction(articles: List<Article>) {
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        // Beginn der Transaktion: der Autocommit-Modus wird verlassen
        connection.transactionIsolation = Connection.TRANSACTION_READ_COMMITTED
        connection.autoCommit = false
        try {
            createInsertStatement(connection).use { statement ->
                articles.forEach { insertArticle(statement, it) }
            }
            // alles ist gut gegangen: die Transaktion wird bestätigt
            connection.commit()
            println("transaction committed...")
        } catch (ex: SQLException) {
            // ein Einfügen ist fehlgeschlagen: die Transaktion wird rückgängig gemacht
            connection.rollback()
            println("transaction rolled back (${ex.message})")
        }
    }
}

// Einfügen in einer Transaktion: der Fehlschlag eines Einfügens macht nur das rückgängig, was
// dem letzten Savepoint folgt
private fun insertArticlesWithSavepoint(articles: List<Article>) {
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.autoCommit = false
        try {
            createInsertStatement(connection).use { statement ->
                for (article in articles) {
                    // ein Savepoint vor jedem Einfügen
                    val beforeInsertion = connection.setSavepoint()
                    try {
                        insertArticle(statement, article)
                    } catch (ex: SQLException) {
                        // nur das fehlgeschlagene Einfügen wird rückgängig gemacht
                        connection.rollback(beforeInsertion)
                        println("insertion of [${article.name}, ${article.price}] cancelled (${ex.message})")
                    }
                }
            }
            connection.commit()
            println("transaction committed...")
        } catch (ex: SQLException) {
            connection.rollback()
            println("transaction rolled back (${ex.message})")
        }
    }
}

// Einfügen in einer Transaktion, verwaltet von der Funktion [transaction]: die Exceptions werden weitergegeben
private fun insertArticlesWithFunction(articles: List<Article>) {
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        val nbArticles = connection.transaction(Connection.TRANSACTION_READ_COMMITTED) {
            // im Block ist [this] die Verbindung
            createInsertStatement(this).use { statement ->
                articles.forEach { insertArticle(statement, it) }
            }
            articles.size
        }
        println("transaction committed: $nbArticles article(s) inserted")
    }
}

// die parametrisierte Anweisung, die einen Artikel einfügt
private fun createInsertStatement(connection: Connection): PreparedStatement = connection.prepareStatement(
    "insert into articles(name, price, currentstock, minimumstock) values(?, ?, ?, ?)"
)

// Einfügen eines Artikels mit der parametrisierten Anweisung
private fun insertArticle(statement: PreparedStatement, article: Article) {
    with(article) {
        statement.setString(1, name)
        statement.setBigDecimal(2, price)
        statement.setInt(3, currentStock)
        statement.setInt(4, minimumStock)
        statement.executeUpdate()
        println("article [$name, $price] inserted")
    }
}

// Ausführung einer update-Anweisung
private fun executeUpdate(query: String) {
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.createStatement().use { statement ->
            println("${statement.executeUpdate(query)} row(s) modified")
        }
    }
}

// Anzeige des Inhalts der Tabelle
private fun displayArticles() {
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.createStatement().use { statement ->
            val query = "select id, name, price, currentstock, minimumstock from articles"
            statement.executeQuery(query).use { result ->
                println("Content of the [articles] table:")
                while (result.next()) {
                    // im with-Block ist [this] das Ergebnis: getInt(1) ist result.getInt(1)
                    val row = with(result) {
                        "${getInt(1)} ${getString(2)} ${getBigDecimal(3)} ${getInt(4)} ${getInt(5)}"
                    }
                    println("  $row")
                }
            }
        }
    }
}

// - bestätigt, wenn der Block normal endet;
// - zurückgesetzt, wenn er eine Exception wirft, die dann erneut geworfen wird;
// der Autocommit-Modus der Verbindung wird am Ende wiederhergestellt
// [crossinline]: der Block darf kein return enthalten, das die aufrufende Funktion verlassen würde
inline fun <T> Connection.transaction(isolation: Int? = null, crossinline block: Connection.() -> T): T {
    // der eventuelle Isolationsgrad wird vor dem Beginn der Transaktion gesetzt
    isolation?.let { transactionIsolation = it }
    val initialAutoCommit = autoCommit
    autoCommit = false
    try {
        val result = block()
        commit()
        return result
    } catch (e: Throwable) {
        try {
            rollback()
        } catch (ex: SQLException) {
            // der Fehlschlag des Rollbacks darf die ursprüngliche Exception nicht verdecken
            e.addSuppressed(ex)
        }
        throw e
    } finally {
        autoCommit = initialAutoCommit
    }
}
    • Zeile 11: Die Funktion [transaction] ist eine Erweiterungsfunktion der Schnittstelle [Connection]: Sie wird als Methode der Verbindung aufgerufen, [connection.transaction { … }]. Sie hat zwei Parameter:
      • [isolation], die Isolationsstufe, vom Typ [Int?] und mit dem Standardwert [null] (in diesem Fall bleibt die Stufe der Verbindung unverändert);
      • [block], die in der Transaktion auszuführende Aufgabe. Ihr Typ [Connection.() -> T] ist der eines Lambdas mit Empfänger: Innerhalb des Blocks ist [this] die Verbindung, und [prepareStatement(…)] kann statt [connection.prepareStatement(…)] geschrieben werden. Das ist der Mechanismus, den [with], [apply], und [buildList] in der Standardbibliothek verwenden. Der Block gibt einen Wert vom Typ [T] zurück, den [transaction] wiederum zurückgibt. Da der Block der letzte Parameter ist, wird er beim Aufruf nach den Klammern geschrieben oder ganz ohne Klammern, wenn er das einzige Argument ist;
    • [inline]: Der Code der Funktion und der Code des Blocks werden an die Aufrufstelle kopiert (Kapitel 7): Für jede Transaktion wird kein Lambda-Objekt erzeugt. Allerdings kann ein Lambda, das an eine [inline]-Funktion übergeben wird, ein [return] enthalten, das die aufrufende Funktion verlässt (ein „nicht lokales“ Return, wie im Rumpf einer Schleife). Hier wäre das eine Falle: Ein *[return] mitten im Block würde das *[try] verlassen, ohne weder [commit] noch *[rollback]* zu durchlaufen, und die Transaktion bliebe offen. Der Modifikator [crossinline] für den Parameter [block] verhindert dies. Der Compiler lehnt daher einen Block wie [connection.transaction { if (name.isEmpty()) return … }] ab:

// Ausführung eines Selects, das einen einzelnen Wert zurückgibt: erste Spalte der ersten Zeile
// das Ergebnis ist null, wenn das Select keine Zeile zurückgibt oder wenn der Wert SQL NULL ist
private fun singleValue(query: String): Any? =
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.createStatement().use { statement ->
            statement.executeQuery(query).use { result ->
                if (result.next()) result.getObject(1) else null
            }
        }
    }

// dasselbe, wobei der Wert vom Treiber in den angeforderten Typ T konvertiert wird
// [reified]: der Typ T ist zur Laufzeit bekannt, T::class.java ist die Java-Klasse von T
private inline fun <reified T : Any> typedSingleValue(query: String): T? =
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.createStatement().use { statement ->
            statement.executeQuery(query).use { result ->
                if (result.next()) result.getObject(1, T::class.java) else null
            }
        }
    }

// der einfache Name der Klasse eines Objekts
private fun type(obj: Any?): String = obj?.let { it::class.simpleName } ?: "null"

    10.8. JDBC blockiert: virtuelle Threads und Coroutinen

    10.8.1. Virtuelle Threads

    Kapitel 9 hat gezeigt, dass E/A-Operationen in Anwendungen, die viele Benutzer bedienen (Server, Webdienste), keinen Anwendungs-Thread blockieren dürfen: Während ein SQL-Befehl auf dem Server ausgeführt wird, wartet der Thread, der ihn abgesetzt hat. Allerdings ist JDBC eine blockierende API: [getConnection], [executeQuery], [next], [commit] … geben die Kontrolle erst zurück, wenn das DBMS geantwortet hat. Es gibt keine asynchrone Version von JDBC: Ein Projekt für eine asynchrone API (ADBA) wurde 2019 aufgegeben, und die reaktive API R2DBC – die unabhängig vom JDK existiert – hat JDBC nicht abgelöst. Es gibt auch keine „suspendierende“ Version von JDBC für Coroutinen: Eine JDBC-Funktion, die innerhalb einer Coroutine aufgerufen wird, blockiert den Thread, der die Coroutine ausführt.

    Seit Java 21 besteht die Lösung der Java-Plattform im virtuellen Thread (Kapitel 8): ein leichtgewichtiger, von der JVM verwalteter Thread, von dem Tausende erzeugt werden können. Wenn ein virtueller Thread auf eine Netzwerkantwort wartet, legt die JVM ihn beiseite und gibt den Systemthread frei, der ihn ausgeführt hat, sodass dieser einen anderen virtuellen Thread ausführen kann. Der Code bleibt sequenziell und blockierend – einfach zu schreiben und zu lesen –, doch das Warten verursacht keinen Mehraufwand mehr. Neuere JDBC-Treiber, darunter Connector/J 9, sind für den Betrieb mit virtuellen Threads geschrieben, und seit Java 24 (JEP 491) blockiert ein virtueller Thread, der in einem [synchronized]-Block wartet, den Systemthread nicht mehr. Kotlin, das auf der JVM läuft, profitiert davon, ohne etwas Besonderes tun zu müssen.

    Eine Einschränkung bleibt: die Anzahl der Verbindungen. Tausend virtuelle Threads, die die Datenbank abfragen, haben nicht tausend Verbindungen; sie teilen sich die Verbindungen des Pools und warten, bis eine Verbindung frei wird.             // die Zeile bleibt gesperrt
            dataSource.connection.use { blocking ->
                blocking.autoCommit = false
                blocking.createStatement().use { statement ->
                    statement.executeUpdate("update articles set currentstock = currentstock - 1 where id = 1")
                }

                val stopwatch = TimeSource.Monotonic.markNow()
                try {
                    dataSource.connection.use { connection ->
                        connection.createStatement().use { statement ->
                            statement.queryTimeout = 1
                            statement.executeUpdate("update articles set price = price * 2 where id = 1")
                        }
                    }

        println("Database access error (${ex.message})")
    } catch (ex: ExecutionException) {
        println("Database access error (${ex.message})")

    10.9. Batch-Ausführung

    Jede Ausführung eines SQL-Befehls verursacht einen Hin- und Rückweg zwischen der Anwendung und dem Server. Müssen mehrere SQL-Befehle ausgeführt werden, können sie in einem einzigen Austausch an das DBMS gesendet werden, in Form eines Batches. JDBC unterstützt dies seit Version 2.0:

    • bei einem [Statement] fügt [addBatch(sql)] dem Batch einen SQL-Befehl hinzu;
    • bei einem [PreparedStatement] fügt [addBatch()] die aktuellen Parameterwerte dem Batch hinzu: Der Batch enthält denselben SQL-Befehl, ausgeführt mit verschiedenen Werten;
    • [executeBatch] führt den Batch aus und gibt ein Array von Ganzzahlen zurück ([IntArray] in Kotlin): die Anzahl der Zeilen, die von jedem Befehl des Batches geändert wurden. Schlägt ein Befehl fehl, löst die Methode eine [BatchUpdateException] aus, deren Methode [getUpdateCounts] (die Eigenschaft [updateCounts] in Kotlin) die Ergebnisse der ausgeführten Befehle zurückgibt.

// Einfügen von n Artikeln durch einen Batch, in einer Transaktion, dann Löschen dieser Artikel
private fun insertBatch(url: String, n: Int) {
    DriverManager.getConnection(url, USER, PASSWORD).use { connection ->
        // measureTimedValue gibt den Wert des Blocks und seine Ausführungszeit zurück
        val (nbRows, duration) = measureTimedValue {
            connection.transaction {
                prepareStatement(
                    "insert into articles(name, price, currentstock, minimumstock) values(?, ?, ?, ?)"
                ).use { statement ->
                    for (i in 1..n) {
                        statement.setString(1, "batch-$i")
                        statement.setBigDecimal(2, BigDecimal.TEN)
                        statement.setInt(3, i)
                        statement.setInt(4, 0)
                        // die Werte der Parameter werden zum Batch hinzugefügt
                        statement.addBatch()
                    }
                    statement.executeBatch()
                }
            }
        }
        val database = url.substringAfterLast('/')
        val ms = duration.inWholeMilliseconds
        println("${nbRows.size} insertions ($database) in $ms ms : ${nbRows.take(3)}...")
        // die Tabelle wird in ihren vorherigen Zustand zurückversetzt
        connection.createStatement().use { statement ->
            statement.executeUpdate("delete from articles where name like 'batch-%'")
        }
    }
}

import java.math.BigDecimal
import java.sql.DriverManager
import java.sql.SQLException
import javax.sql.rowset.RowSetProvider

// getrennter Modus: eine In-Memory-Kopie der Zeilen, offline geändert und dann an die Datenbank zurückgesendet

private const val URL = "jdbc:mysql://localhost:3306/dbarticles"
private const val USER = "root"
private const val PASSWORD = ""

fun main() {
    try {
        // die RowSet-Factory der Java-Plattform
        val factory = RowSetProvider.newFactory()
        factory.createCachedRowSet().use { articles ->
            // die Verbindungsparameter und die Query
            articles.url = URL
            articles.username = USER
            articles.password = PASSWORD
            articles.command = "select id, name, price, currentstock, minimumstock from articles"
            // die zu aktualisierende Tabelle und ihr Primärschlüssel (Spalte Nr. 1)
            articles.tableName = "articles"
            articles.keyColumns = intArrayOf(1)
            // Verbindung, Kopie der Zeilen in den Speicher, Trennung
            articles.execute()
            println("${articles.size()} rows copied into memory")

            // Offline-Arbeit: Auffüllen der vergriffenen Artikel
            while (articles.next()) {
                val currentStock = articles.getInt("currentstock")
                val minimumStock = articles.getInt("minimumstock")
                if (currentStock < minimumStock) {
                    articles.updateInt("currentstock", minimumStock + 10)
                    articles.updateRow()
                    val name = articles.getString("name")
                    println("[$name] : stock $currentStock -> ${articles.getInt("currentstock")}")
                }
            }
            // Hinzufügen einer Zeile: die id 0 fordert MySQL auf, eine zu erzeugen
            with(articles) {
                moveToInsertRow()
                updateInt("id", 0)
                updateString("name", "canoe")
                updateBigDecimal("price", BigDecimal("800"))
                updateInt("currentstock", 5)
                updateInt("minimumstock", 1)
                insertRow()
                moveToCurrentRow()
            }
            // Löschen der 2. Zeile
            articles.absolute(2)
            println("deletion of [${articles.getString("name")}]")
            articles.deleteRow()

            // die Datenbank wurde noch nicht geändert
            displayArticles("Database before acceptChanges:")
            // Verbindung, Senden der Änderungen in einer Transaktion, Trennung
            DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
                connection.autoCommit = false
                articles.acceptChanges(connection)
            }
        }
        displayArticles("Database after acceptChanges:")
    } catch (ex: SQLException) {
        println("Database access error (${ex.message})")
    }
}

// Anzeige des Inhalts der Tabelle, im verbundenen Modus gelesen
private fun displayArticles(title: String) {
    DriverManager.getConnection(URL, USER, PASSWORD).use { connection ->
        connection.createStatement().use { statement ->
            val query = "select id, name, price, currentstock, minimumstock from articles"
            statement.executeQuery(query).use { result ->
                println(title)
                while (result.next()) {
                    val row = with(result) {
                        "${getInt(1)} ${getString(2)} ${getBigDecimal(3)} ${getInt(4)} ${getInt(5)}"
                    }
                    println("  $row")
                }
            }
        }
    }
}

    • Zeilen 17–18: [RowSetProvider.newFactory] (Java 7) liefert eine Factory ([RowSetFactory]) für die verschiedenen RowSet-Typen des JDK; eine ihrer Methoden, [createCachedRowSet], erzeugt ein [CachedRowSet]. Ein [CachedRowSet] ist eine Ressource ([AutoCloseable], wie jedes [ResultSet]), die durch [use] geschlossen wird;
    • Zeilen 20–23: [CachedRowSet] erhält die Verbindungsparameter und die Abfrage, die es füllen wird. Die Methoden [setUrl], [setUsername], [setPassword] und [setCommand] haben jeweils einen zugehörigen Accessor, [getXxx]: Kotlin stellt sie als Eigenschaften dar;
    • Zeilen 25–26: Um die Änderungen an die Datenbank zurückschicken zu können, muss es die geänderte Tabelle und ihren Primärschlüssel kennen – hier die Spalte 1, [id]. [intArrayOf(1)] erzeugt das Array [int[]] , das die Java-Methode erwartet;
    • Zeile 28: [execute] öffnet eine Verbindung, führt die Abfrage aus, kopiert alle Zeilen des Ergebnisses in den Speicher und schließt die Verbindung. Die übrige Arbeit erfolgt offline. [articles.size()] (Zeile 29) liefert die Anzahl der Zeilen: Da [size] kein Accessor für [getSize] ist, bleibt es eine Methode;
    • Zeilen 32–39: Ein [CachedRowSet] ist ein [ResultSet]: Wir durchlaufen es mit [next] und lesen die Spalten mit [getXxx]. Die Methoden [updateXxx] ändern eine Spalte der aktuellen Zeile, und [updateRow] speichert die Änderung … in der Kopie im Speicher. Der Bestand an Pfeilen, der unter dem Mindestbestand liegt, wird auf 30 erhöht (Zeile 3 der Ergebnisse);
    • Zeilen 43–51: Hinzufügen einer Zeile. Alle acht Aufrufe verwenden [CachedRowSet]: Die Funktion [with] bestimmt es zum Empfänger des Blocks, wodurch die Wiederholung von [articles.] entfällt. [moveToInsertRow] setzt den Cursor auf eine spezielle Zeile, die „Einfügezeile“, deren Spalten durch [updateXxx] festgelegt werden; [insertRow] fügt sie dem [CachedRowSet] hinzu, und [moveToCurrentRow] setzt den Cursor auf seine vorherige Position zurück. [CachedRowSet] verlangt einen Wert für alle [NOT NULL]-Spalten, einschließlich [id]: Der Wert 0, in eine [AUTO_INCREMENT]-Spalte eingefügt, weist MySQL an, einen zu erzeugen;
    • Zeilen 54–56: [absolute(2)] setzt den Cursor auf die zweite Zeile, was durch [CachedRowSet] ermöglicht wird – der Cursor kann sich in jede Richtung bewegen –, und [deleteRow] löscht sie;
    • Zeile 59: Die Datenbank wurde noch nicht geändert (Zeilen 5–11 der Ergebnisse);
    • Zeilen 61–63: [acceptChanges] überträgt die Änderungen in die Datenbank: ein [update], ein [insert] und ein [delete], ausgeführt in einer Transaktion, die am Ende committet wird. Für jede geänderte Zeile prüft die JDK-Implementierung, dass die Datenbankzeile seit dem Lesen nicht von jemand anderem geändert wurde (eine „optimistische“ Prüfung); andernfalls löst sie eine [SyncProviderException] aus. Die parameterlose Version von [acceptChanges] öffnet die Verbindung selbst, belässt sie aber im Autocommit-Modus und ruft dann [commit] auf, was Connector/J ablehnt; deshalb wird ihr eine Verbindung übergeben, die den Autocommit-Modus verlassen hat;
    • Zeile 66: Die Datenbank wurde geändert (Zeilen 12–18 der Ergebnisse).

    [CachedRowSet] hat den Vorteil, eine Standard-API des JDK zu sein, doch seine Grenzen sind offensichtlich: Es manipuliert Zeilen sowie Spaltennamen oder -nummern statt Geschäftsobjekten; Änderungen erfolgen über eine Implementierung, bei der wir nur begrenzte Kontrolle über das SQL haben. Deshalb wird es heute selten verwendet: Das Arbeiten mit Objekten im Speicher und das anschließende Speichern der Änderungen ist die Domäne von ORM-Frameworks wie Hibernate (Kapitel 11).

import tax.entities.TaxException
import tax.entities.TaxBracket
import java.math.BigDecimal
import java.sql.DriverManager
import java.sql.ResultSet
import java.sql.SQLException

// eine [dao]-Schicht, die die Steuerstufen aus einer MySQL-Datenbank liest
// die Query hat einen Standardwert: ein einziger Konstruktor genügt
class MySqlTax(
    url: String,
    user: String,
    password: String,
    query: String = DEFAULT_QUERY,
) : ITaxDao {

    // Steuerstufen, einmalig bei der Konstruktion des Objekts gelesen
    override val taxBrackets: List<TaxBracket>

    init {
        val brackets: List<TaxBracket> = try {
            DriverManager.getConnection(url, user, password).use { connection ->
                connection.createStatement().use { statement ->
                    statement.executeQuery(query).use { result ->
                        // eine Stufe pro Zeile des Ergebnisses: limit, coeffR, coeffN
                        buildList {
                            while (result.next()) {
                                add(readBracket(result))
                            }
                        }
                    }
                }
            }
        } catch (e: SQLException) {
            // Datenbankzugriffsfehler: er wird in eine TaxException verpackt
            throw TaxException("Error accessing the tax brackets database", e, ACCESS)
        }
        // eine leere Tabelle ist ebenfalls ein Fehler
        if (brackets.isEmpty()) {
            throw TaxException("The database contains no tax bracket", code = DATA)
        }
        // buildList gibt eine schreibgeschützte Liste zurück
        taxBrackets = brackets
    }

    companion object {
        // für diese Implementierung spezifische Fehlercodes
        const val ACCESS = 101
        const val DATA = 102

        // die Standard-Query: die Stufen müssen in aufsteigender Reihenfolge der Grenzen zurückgegeben werden
        const val DEFAULT_QUERY = "select limits, coeffr, coeffn from brackets order by id"

        // die Stufe der aktuellen Zeile: drei numerische Spalten, ohne NULL-Wert
        private fun readBracket(result: ResultSet): TaxBracket {
            // getBigDecimal gibt für einen SQL-NULL-Wert null zurück: der Typ ist also BigDecimal?
            val columns: List<BigDecimal?> = try {
                (1..3).map { result.getBigDecimal(it) }
            } catch (e: SQLException) {
                // eine fehlende oder nicht numerische Spalte
                throw TaxException("The tax brackets of the database are incorrect", e, DATA)
            }
            val (limit, coeffR, coeffN) = columns
            if (limit == null || coeffR == null || coeffN == null) {
                throw TaxException("A tax bracket of the database has a NULL value", code = DATA)
            }
            // hier sind die drei Werte vom Typ BigDecimal (Smart Cast)
            return TaxBracket(limit, coeffR, coeffN)
        }
    }
}

    • Zeilen 12–17: Der primäre Konstruktor erhält die Verbindungsparameter und die Abfrage, die die Stufen liefert. Die Abfrage hat einen Standardwert, [DEFAULT_QUERY]: Wo Java zwei Konstruktoren benötigte – der zweite rief den ersten über [this(…)] auf –, genügt in Kotlin einer. Die Parameter sind keine Eigenschaften (sie haben weder [val] noch [var]): Sie werden nur zum Konstruieren des Objekts verwendet, und das Passwort wird nicht gespeichert;
    • Zeile 20: die Eigenschaft des Interfaces [ITaxDao], die die Klasse überschreibt. Sie hat keinen Anfangswert: Ihr Wert wird im [init]-Block ein für alle Mal zugewiesen;
    • Zeile 22: Die Stufen werden bei der Konstruktion des Objekts ein für alle Mal gelesen: Die Schicht [dao] ist in der Anwendung ein Singleton, und die Datenbank wird danach nicht mehr abgefragt. Eine von [DriverManager] geöffnete Verbindung genügt daher: Ein Verbindungspool wäre sinnlos;
    • Zeilen 23–26: die Verbindung, der SQL-Befehl und das Ergebnis, eingeschlossen von drei verschachtelten [use]-Anweisungen, wie in den vorherigen Beispielen. [try] ist ein Ausdruck: Sein Wert – der der verschachtelten Blöcke – wird zum Wert von [brackets];
    • Zeilen 28–30: Die Funktion [buildList] aus der Standardbibliothek konstruiert eine Liste: Innerhalb ihres Blocks ist [this] eine veränderbare Liste, der [add] pro Ergebniszeile eine Stufe hinzufügt; anschließend gibt sie diese Liste als Typ [List] zurück, schreibgeschützt. Der Typ der Variablen, [List<TaxBracket>], wird ausdrücklich angegeben: Der Compiler muss den Typ der Listenelemente kennen, bevor er den Block analysiert;
    • Zeilen 36–38: Ein Fehler beim Datenbankzugriff wird in eine [TaxException] mit dem Code [ACCESS] gekapselt, genau wie [FileTax] und [JsonTax] es bei Ein-/Ausgabefehlern taten. Die Schicht [ui] muss weder die [SQLException] noch JDBC kennen;
    • Zeilen 41–42: Eine leere Tabelle ist ein Datenfehler. Die [TaxException] aus Kapitel 6 hat nur einen Konstruktor, [TaxException(message, cause = null, code = 0)]: Um einen Code ohne Ursache zu erzeugen, muss das Argument [code] angegeben werden;
    • Zeile 45: Die Eigenschaft erhält die Liste der Stufen;
    • Zeilen 48–51: für diese Implementierung spezifische Fehlercodes, nach dem Vorbild derer von [FileTax] und [JsonTax]: 101 für einen Datenbankzugriffsfehler, 102 für fehlerhafte Daten. Es sind Konstanten ([const val]) des Companion-Objekts: Man verweist auf sie als [MySqlTax.ACCESS];
    • Zeile 54: die Abfrage, die die Stufen liefert. Die Klausel [order by id] ist wichtig: Die Schicht [business] erwartet die Stufen in aufsteigender Reihenfolge der Grenzen, und ein [select] ohne [order by] liefert die Zeilen in einer Reihenfolge, die SQL nicht garantiert;
    • Zeile 57: das Lesen einer Stufe, eine private Funktion des Companion-Objekts (sie verwendet keine Eigenschaften des Objekts):
      • Zeilen 59–60: [getBigDecimal(i)] liest die Spalte mit der Nummer i als [BigDecimal]. Der deklarierte Typ, [List<BigDecimal?>], ist wichtig: Für Kotlin liefert eine Java-Methode einen Wert des „Plattformtyps“ [BigDecimal!], und Kotlin weiß nicht, ob er [null] sein kann. Allerdings [getBigDecimal] liefert [null] für einen SQL-Wert [NULL]: Indem wir Elemente vom Typ [BigDecimal?] deklarieren, zwingen wir den Compiler, uns diesen Fall prüfen zu lassen;
      • Zeilen 61–63: Eine Abfrage, die weniger als drei Spalten oder eine nicht numerische Spalte liefert, verursacht eine [SQLException] in [getBigDecimal]: Auch das ist ein Datenfehler;
      • Zeilen 65–67: Die Liste wird in drei Variablen destrukturiert; ein Wert vom Typ [null] ist ein Datenfehler;
      • Zeile 70: Nach der Prüfung haben die drei Variablen den Typ [BigDecimal] und nicht mehr [BigDecimal?] (Smart Cast): Der Compiler akzeptiert ihre Übergabe an den Konstruktor von [TaxBracket], der Werte ungleich null erwartet. Ohne die Prüfung hätte er die Kompilierung verweigert. Die [TaxException], die von [readBracket] instanziiert wird, ist keine [SQLException]: Sie passiert das [catch] im Block [init], ohne abgefangen zu werden, und die drei [use]-Aufrufe schließen dennoch das Ergebnis, den Befehl und die Verbindung.

    10.11.6. Die Datenbank wechseln

    Die [dao]-Schicht ([MySqlTax]) verwendet nur die Interfaces von JDBC: Trotz ihres Namens ist sie nicht MySQL-spezifisch (ein Name wie [JdbcTax] wäre passender). Um eine PostgreSQL-Datenbank (oder SQL Server oder Oracle) zu verwenden, genügt es:

    • in einer PostgreSQL-Datenbank die Stufentabelle anzulegen – zum Beispiel eine Tabelle namens [data] mit den Spalten [data1], [data2], [data3], um den Nutzen der Abfrage in der Konfiguration hervorzuheben;

    10.12. Fazit

    Dieses Kapitel hat den Datenbankzugriff über JDBC aus Kotlin behandelt:

    • JDBC ist eine Menge von Interfaces ([Connection], [Statement], [PreparedStatement], [ResultSet], [DataSource] …) aus den Paketen [java.sql] und [javax.sql] , die von einem Treiber implementiert werden, der für jedes DBMS spezifisch ist (MySQL Connector/J für MySQL) und den [DriverManager] anhand der JDBC-URL der Datenbank auswählt. Kotlin hat keine eigene API: Es verwendet JDBC direkt, wobei seine Accessoren als Eigenschaften behandelt werden ([connection.autoCommit = false]);
    • Eine Verbindung wird so spät wie möglich geöffnet und so früh wie möglich geschlossen, mittels der Funktion [use]; ein Verbindungspool wie HikariCP, über das Interface [DataSource], macht diese Praxis kostengünstig;
    • [executeQuery] führt ein [select] aus und gibt ein [ResultSet], zurück, das zeilenweise mit [next] durchlaufen wird, wobei die Spalten, nummeriert ab 1, mit den Methoden [getXxx] gelesen werden; Erweiterungsfunktionen ([toList], [asSequence], [toArticle]) wandeln die Zeilen in Kotlin-Objekte um. [executeUpdate] führt ein [insert], [update], oder [delete] aus und gibt die Anzahl der geänderten Zeilen zurück;
    • Fehler sind [SQLException]-Exceptions, die einen DBMS-spezifischen Fehlercode und einen standardisierten SQLSTATE-Code liefern. Sie müssen in Java behandelt werden, nicht jedoch in Kotlin, das keine Vorgaben macht: Es ist Sache des Entwicklers zu entscheiden, wo er sie abfängt, typischerweise in der Schicht [dao], die sie in eigene Exceptions kapselt;
    • Externe Werte werden stets über die Parameter eines [PreparedStatement] übergeben und niemals in den Abfragetext eingefügt – weder durch Verkettung noch über ein String-Template –, was vor SQL-Injection schützt;
    • Transaktionen ([autoCommit = false], [commit], [rollback], Savepoints) machen eine Folge von SQL-Befehlen atomar; eine Funktion höherer Ordnung wie unser [connection.transaction { … }] verbirgt die inneren Abläufe;
    • JDBC blockiert: virtuelle Threads erlauben es, mit gewöhnlichem JDBC-Code viele Benutzer zu bedienen, innerhalb der Grenzen der Poolgröße; Coroutinen integrieren dies, indem sie Aufrufe in [withContext(Dispatchers.IO)] verpacken, vorzugsweise mit einer auf die Poolgröße begrenzten Parallelität. Batches ([addBatch], [executeBatch]) verringern die Zahl der Austausche mit dem Server;
    • Der Offline-Modus ([CachedRowSet]) existiert, doch die Arbeit mit Objekten im Speicher ist inzwischen die Domäne von ORMs.

    Version 6 der Anwendung [Tax] hat gezeigt, dass der Wechsel von einer Datei zu einer Datenbank dank der Schichtenarchitektur nur das Schreiben einer neuen [dao]-Schicht und eine Änderung der Konfiguration erfordert; das Build-System Gradle hat es uns erlaubt, Version 5 wiederzuverwenden, ohne sie zu kopieren oder zu installieren. Im nächsten Kapitel erstellen wir mit Hibernate, das die SQL-Befehle selbst generiert, eine siebte Version dieser Schicht.

    Zwischen dem „rohen“ JDBC dieses Kapitels und einem vollständigen ORM wie Hibernate bietet das Kotlin- und Java-Ökosystem Bibliotheken auf mittlerer Ebene, die die Kontrolle über das SQL behalten und wiederholten Code beseitigen:

    • Exposed, die Datenbankzugriffsbibliothek von JetBrains, in Kotlin geschrieben: Tabellen werden durch Kotlin-Objekte beschrieben, und Abfragen werden in einer dedizierten, typisierten Sprache (DSL) geschrieben, [Articles.selectAll().where { Articles.price less 200 }], innerhalb von [transaction { … }]-Blöcken; sie bietet außerdem eine Objektschicht (DAO), die einem ORM näherkommt;
    • jOOQ, das aus dem Datenbankschema Java-Klassen generiert, die aus Kotlin verwendet werden können, und es erlaubt, SQL-Abfragen zu schreiben, die zur Kompilierzeit überprüft werden;
    • Spring JDBC, dessen Interface [JdbcClient] (Spring 6.1) eine parametrisierte Abfrage ausführt und ihre Zeilen in einer einzigen fließenden Anweisung in Objekte umwandelt, während es Verbindungen, Schließvorgänge und Exceptions verwaltet.
